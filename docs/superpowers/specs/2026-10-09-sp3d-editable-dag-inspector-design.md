## Goal

Make the terrain editable as data. The default density expression and the default surface-rule tree become two schema leaves of a new `json` kind, whose defaults are today's trees written as data and whose numbers reference the existing parameters, so every slider keeps working on an edited tree. An edited tree is validated as untrusted JSON before it reaches the generator, travels through the session (undo, URL, presets, live preview) like any other parameter, and is inspected in a new **Density** drawer tab of `?map`: a node tree, a node form, a JSON editor and a slice viewer that shows the final density, any selected node or the blocks on a vertical or horizontal plane, re-rendered on every edit. With the defaults the world is bit-identical: no voxel, tile, metric or golden changes. SP3e then designs the three draft presets on this tooling.

## Non-goals

- The draft presets `floating_islands`, `amplified` and `archipelago` (their terms, splines, params, the islands surface-rule branch, island-edge springs, Z1-Z3, per-preset goldens and B1's ocean-cap gating for archipelago): the new SP3e (Decision 1, §14).
- A visual (node-graph) editor: out of scope in the master (§5.5).
- Caves, cave terms, the level fields' −∞ interval rule and `caveBiome`: SP6. The default trees gain no term here.
- Pinned slices (up to 3 side by side): the cut line (§11), received by SP10 if cut.
- The slice view of every 3D field, the 256² refinement, the full probe and the JSON editors of placed features and structure sets/pools: SP10 (master §10 SP10).
- `stoneDepth.secondaryDepthRange` (SP3c §3.1, handed to SP3d by SP3c §11 "when a default rule needs it"): no default rule needs it, so it stays an unknown field and stays with SP6, whose cave floor and ceiling rules are its first likely user (§13).
- Any change of the world: the default trees resolve to exactly the trees the code builds today (§2), and `GENERATOR_VERSION` stays 5 (§8).
- The 2D map layers: they are upstream of the `terrain` stage, so tree edits never change them (§1.5).

## Decisions taken by this spec (for the user's review)

The brief left these open or the code survey and the review forced them. Each states its alternative; the recommendation is the text of the section cited.
- **D1 Leaf kind `json` with a format.** One new kind `json` (as the brief says) whose leaf carries `format: 'density' | 'surfaceRules'`; the master's reserved kinds `'expr'` and `'ruleTree'` (`src/core/params/kit.ts:12-13`, master §2.5) are removed, since nothing uses them. The schema-shape lock records `json:<format>` so a format switch is a shape change (§1.1). Alternative: reuse the two reserved kinds (no discriminator needed, but two kinds for one mechanism).
- **D2 Two-tier validation without a layer change** (§1.7, §1.8). Core cannot import gen or world (`test/arch/rules/imports.ts:16`) and the engine imports gen as types only (`imports.ts:28`), while the validators need gen's and world's vocabularies. Tier 1 (core, inside `checkLeaf`) guarantees a canonical-safe, bounded JSON value; tier 2 (gen) is the full semantic validation, run by the worker at configure, injected into `WorldSession` through a constructor option that the UI wires (and run by the session's constructor, `setProfile`, `commitPatch`, `load` and `restore`), and run again by the resolvers themselves, so no caller can compile a tree that has not passed it. Alternatives: move the validators and their vocabularies (sample fields, biome names, block states and solidity) into core, or let the engine value-import gen.
- **D3 Leaf shapes and paths** (§1.2). `density.defs` holds the whole `{root, defs}` expression; `surface.rules` holds the root rule. An issue path is the leaf path, a dot, then the format's node path (`density.defs.root.a.x`, `surface.rules.root.rules[1].then.if.min`); an issue at the value itself carries the leaf path alone.
- **D4 Parameter refs in every numeric field** (§1.3), as brief §2 says. Targets: the `number` and `int` leaves under `density.` and `surface.`, and the `clampSigma` field of their noise leaves. Every check that involves a ref holds for the target's whole static range, so a slider move can never invalidate a stored tree. In density a `param` node stands where a `const` would, and every numeric scalar field (`clamp` and `rangeChoice` bounds, `slide` knot coordinates, `tap.mute`) may hold `{param}` or `{param, neg: true}`, exactly as the rules' numeric fields do; an int field takes only `int` leaves. Alternative (the first draft's): scalar fields stay literal, so the order checks stay static; rejected because it narrows the brief.
- **D5 Source-only forms.** `param`, `recip`, tap `mute` and ref-valued fields exist only in the source tree and are resolved before compilation (§1.6), so `EXPR_OPS`, the compiler, the bounds, the reference evaluator, both op-coverage tests and the `sp3b.density.*` goldens are untouched. `recip` takes a constant operand (a `const`, or a `param` whose range excludes 0).
- **D6 Constant folding at resolution** (§1.6), so that the resolved default is the very tree the code builds (same `exprHash`), as the brief requires.
- **D7 Mute value.** The inspector's toggle writes the neutral value of the tap's parent (§1.5); the value stays editable in the form.
- **D8 NaN-free and sound** (§1.9). Both a static magnitude analysis of the source (literals ≤ 1e9, values ≤ 1e100, every ColumnSample field within a proven bound) and interval "poison" propagation in the bounds; the brief offered one of the two.
- **D9 Bounds** (§1.7): the numbers of every size, depth and cost limit, applied to every def and every muted subtree as well as the root, and a per-column cost bound that keeps the T stage within 64 × the default's cost.
- **D10 Freeze point** (§1.6): the resolver builds a fresh tree and deep-freezes it; the contexts deep-freeze an explicit tree they receive **in place** (a full walk, identity kept), never assert. Not inside `compileDensity` (which would break the identity-keyed APIs, `src/gen/density/compile.ts:106-107`). The brief said "cloned and frozen on compile"; the clone happens at resolution, which is where every edited tree comes from.
- **D11 Fast-path contract** (§1.10): `scanColumn` clamps the depth noise and `surfaceScanSettings` refuses `depthMul < 0`.
- **D12 `SCHEMA_VERSION` 2** with an identity migration and the two U4 fixtures (§1.11); the bump is not forced by the lock (`test/harness/schemaShape.ts:37-44`) but makes older builds report `NEWER_SCHEMA_VERSION`.
- **D13 URL and history size** (§1.12): atomic leaves, a 128 KiB cap per tree, identity-preserving validation so history snapshots share trees, a 64 KiB URL hash cap with a notice, no finer diff.
- **D14 Goldens** (§8): `sp1.params` hashes a frozen fixture schema, so the new leaves cannot move it; `GENERATOR_VERSION` stays 5 and `test/goldens.json` stays byte-identical. The brief's conditional is stated both ways.
- **D15 U2 and DT2** (§7): the exact perturbations of the two leaves, and two new DT2 parts for edited trees.
- **D16 Slice geometry, fields and costs** (§4, §5): the sample formulas; every density field evaluated by the reference; rule-node masks; horizontal slices from exact four-corner point samples instead of full ColumnSamples (the brief's "one column sample per point" at 16× less cost, measured in `map-workers.md` §7); a deterministic, op-weighted work bound that also charges sample acquisition; same-epoch cancellation of queued parts only (Open point 1); requests triggered by the pool's resolved configure.
- **D17 Hover value job** (§5.3): a new `fieldProbe` worker job (no density probe job exists, `map-workers.md` §2).
- **D18 Inspector UI rules** (§3): tab order and grid, the JSON editor's own printer and parser with its dirty-buffer rule and mirror highlighting, the node-form operations' exact semantics, the cut-line behaviour while Density is shown, readouts as overlays.
- **D19 Hand-overs**: the land-top y mod 16 residue goes to SP6 (§13).
- **D20 The slice evaluation lives in gen** (`src/gen/inspect/`, §5.1), under the determinism rules; the worker only handles messages.

## Points decided by the user after the review (2026-10-10)

The review raised three points that touched the brief's wording; the user confirmed the spec's reading of each on 2026-10-10:
1. **Running slice parts are not interrupted** (brief §3: "any earlier slice still running is cancelled"). A new request drops the earlier request's queued parts and discards the results of its running parts, but a running part finishes (§4.5): interrupting it would need a second abort cell, which breaks the 4-byte abort protocol (`src/workers/protocol.ts:114`). The work bound keeps a density part to about 115 ms, and a `blocks` or `rule` part to one T column (at most 64 × today's, §1.7). **Kept as specified.**
2. **A mute does not change the 2D map** (brief §1 said a mute "affects everything (map, Voxels, slices)"). The map's layers (climate, shape, biomes) are upstream of `terrain` and keyed by their own stage hashes (`src/gen/map/layers.ts:27-31`), so a tree edit shows in the slices, the cross-section's Voxels mode and the hover values, never in the 2D map. The tab says so (§3.1). **Confirmed; no map layer is added.**
3. **Heavy nodes may get only a draft, or no slice.** The work bound (§5.2) refuses a 128² slice of a node whose evaluation costs more than about 14 × the default's, and any slice above about 27 ×; the hover value still works up to the tier-2 bounds. Tier 2 also refuses trees whose T column costs more than 64 × the default's (§1.7). **The factors are kept.**

## 1. Data model

### 1.1 The `json` leaf kind (`src/core/params/kit.ts`, `json.ts`)

- `ParamKind` gains `'json'` and loses the reserved, unused `'expr'` and `'ruleTree'` (`kit.ts:12-13`; master §2.5). `featureList` and `structureSets` stay reserved for SP8b/SP9, which will decide whether they become `json` formats.
- A `json` leaf is built by `jsonLeaf(def, format, meta)` with `merge: 'atomic'` (required: `applyPatch` replaces atomic leaves whole, `kit.ts:445`; `diffParams` compares them whole, `kit.ts:472`; the session's `mergeInto` returns the delta, `src/engine/session.ts:72`). `Leaf` and `ParamMeta` gain `format?: JsonFormat`, present exactly on `json` leaves.
- `checkLeaf` gains `case 'json': return checkJson(v, path, out, leaf.format)` (tier 1, §1.7). It never throws; `undefined` (from `session.set(path, undefined)`, `session.ts:93-99`) is the issue `NOT_JSON`.
- `renderReference` (`kit.ts:506-518`) writes a json leaf's default cell as `<format> tree, <n> nodes` (as `boxTable` writes `N rows`), never the tree itself; its range cell is empty.
- The shape lock records `json:density` and `json:surfaceRules` as the kinds of the two leaves (`currentShape`, `test/harness/schemaShape.ts:17-21`, reads `meta.kind` plus `:format` for json leaves), so a format change is a re-kind and needs a `SCHEMA_VERSION` bump.
- `IssueCode` (`kit.ts:46-51`) gains `JsonIssueCode` (tier 1) and `TreeIssueCode` (tier 2), both string-literal unions declared in `core/params/json.ts`; a type test asserts that gen's `ExprErrorCode` (`src/gen/density/expr.ts:96-98`), `RuleErrorCode` (`src/gen/surface/rules.ts:113-120`) and the new source codes are assignable to `TreeIssueCode`.
- The parameter panel (`panelTree` adds a control for every leaf, `src/ui/paramPanel/model.ts:79-94`; `createControl` throws for other kinds, `controls.ts:465-475`) gains a `treeControl`: the leaf's label, the modified dot and reset, and a link "Edit in Density" that opens the drawer's Density tab on that root (the precedent is `splineControl`, `controls.ts:433-447`). `PANEL_KINDS` gains `'json'`.
- `randomValue` (`test/harness/params.ts:91-123`) returns a json leaf's default and makes **no draw**, and `randomPatch` (`params.ts:143-145`) skips json leaves before drawing their inclusion bit, so every other leaf's random stream is unchanged (`patch.test.ts` keeps its pins); random trees come from the dedicated fuzz (§10).

### 1.2 The two leaves

| leaf | format | value | placement |
|---|---|---|---|
| `density.defs` | `density` | the whole density expression `{root, defs}` (SP3b §1.1's `DensityExpr` top level), in source form (§1.3-§1.5) | TERRAIN (`src/core/params/schema.ts:10`), last in the `density` group |
| `surface.rules` | `surfaceRules` | the root rule (SP3c §3.1's JSON encoding), in source form | TERRAIN, last in the `surface` group |

- Both sit under the `terrain` stage's hashed prefixes `['density', 'surface']` (`src/core/stage/registry.ts:20`), so editing a tree dirties `terrain` and everything after it, and nothing before it (the map tiles' stages keep their hashes).
- **Paths.** An issue's path is the leaf path, a dot, and the format's node path; an empty node path (an issue at the value itself, which `validateExpr` reports at `''`, `expr.ts:101`, `137`) gives the leaf path alone, as the panel's `issueLines` expects (`src/ui/paramPanel/model.ts:226-232`):
  - density: the JSON path inside the value, which is also `validateExpr`'s path syntax (`expr.ts:101-102`): `root`, `root.a.b.x`, `root.knots[2]`, `defs.terrain`, `defs.terrain.x`; so `density.defs.root.a.x` is also a `getPath` path;
  - rules: SP3c's rule ids with their condition and field suffixes (`rules.ts:74-82`, `119`): `root`, `root.rules[1].then`, `root.rules[1].then.if.if`, `.min`, `.biomes[2]`. `root` names the value itself and is not a JSON key, so `surface.rules.root.rules[1]` is not a `getPath` path; the inspector maps an issue to a node by removing the `<leaf>.` prefix (as `src/ui/paramPanel/model.ts:229-230` does).
  - A key rejected by tier 1 (`BAD_KEY`) appears in its path as `JSON.stringify(key)` truncated to 40 characters, so a raw key of any length or with control characters never reaches a notice. Issue and summary text is always set through `textContent` (no `innerHTML` exists under `src/ui/` today, and none is added).
- The group docs "its structure is code until SP3d" (`schema.ts:109`, `118`) become "its structure is the `defs` / `rules` tree".
- Like every leaf, the URL, presets, undo and the session carry only the diff from the profile; an untouched tree is not in the patch. An edited tree counts as one modified parameter (`modifiedCount`, `session.ts:265-273`).

### 1.3 Parameter references

**Targets.** A ref names a path in `ALLOWED_REF_TARGETS` (a `Map`): every leaf of kind `number` or `int` under `density.` or `surface.` (today `density.detailAmpLo`, `density.detailAmpHi`, `surface.depthMul`, `snowline`, `lapse`, `lapseBase`, `cliffSteep`, `cliffMinY`, `patchThreshold`), and the `clampSigma` field of every noise leaf under `density.noises.` and `surface.noises.` (`density.noises.jag.clampSigma`, …; a noise field is not a schema leaf, `kit.ts:143-151`, so the list is built from the schema's noise leaves, never from `getPath`, which would read anything, `kit.ts:486-494`). A target's **static range** is its leaf's `[min, max]`, or `NOISE_FIELD_RANGES.clampSigma` = [1, 8] (`kit.ts:167-174`); every listed target has a finite range. Every target is hashed by the `terrain` stage, so cache invalidation stays sound; a ref to a later stage's leaf would not dirty `terrain`, which is why upstream and later groups are excluded (SP3e may widen the set to the upstream groups, which `terrain` already chains).

**Value-independence.** Validation never reads a target's current value: every check that involves a ref must hold for every value in the ref's static range (a negated ref's range is `[0 − max, 0 − min]`; two refs are treated as independent). A tree that validates stays valid under any slider move, so validity is a pure function of the tree (which `session.restore` needs, §1.8). Two refs to the same leaf on both sides of an order check are therefore judged as independent (for example `noiseThreshold{min: {param t}, max: {param t}}` is rejected); this is conservative and stated in the error message.

**The ref form.** A numeric field may hold, instead of a number, `{"param": "<path>"}` or `{"param": "<path>", "neg": true}`. The resolved value is the target's value v, or `0 − v` when `neg` is true (`0 − 0` is +0, never −0, as `src/gen/surface/defaults.ts:11` writes it today; `−v` or `−1·v` would give −0). `neg` is either absent or `true` (`neg: false` is `BAD_FIELD`, so each ref has one spelling). An int field accepts only `int` targets (`surface.lapseBase`, `surface.cliffMinY`, both [−64, 319]); a number field accepts any target. Every density numeric field is a number field, so `PARAM_KIND` occurs in rules only. A malformed ref (`neg` not `true`, `param` not a string, any other key, `{}`) is `BAD_FIELD`. Every ref issue is reported at the field's path (`root.a.lo`, `root.rules[1].then.if.min`), never at `.param`.

**Density.** A new source op `{op: 'param', path}` is a leaf node whose value is the target's value. It may stand in any child slot (it is COLUMN-class once resolved to a `const`); the inspector offers it on a `const` node, which it replaces (§3.3). `const.v` stays a literal (the `param` node is its ref form). Every other numeric scalar field takes the ref form: `clamp.lo`/`hi`, `rangeChoice.lo`/`hi`, each `slide` knot's y and value, and `tap.mute`. The order checks hold over the static ranges: `CLAMP_ORDER` and `RANGE_ORDER` compare the largest possible `lo` with the smallest possible `hi`; `KNOTS_ORDER` requires every knot's largest y to be below the next knot's smallest y; `SLIDE_SLOPE` (§1.7) is computed from the range endpoints. These are the rules' checks (`GRADIENT_ORDER`, `RANGE_ORDER`) on the same code path.

**Rules.** Each of the nine numeric fields (`stoneDepth.offset`, `water.offset`, `yAbove.minY`, `verticalGradient.trueAtAndBelow` and `.falseAtAndAbove`, `steep.min`, `noiseThreshold.min` and `.max`, `temperatureBelow.t`; `map-surface.md` §3) takes the ref form. Int fields (`offset`, `minY`, the gradient bounds) take only `int` targets, within the rules' [−384, 384]. The `verticalGradient` dither seed is derived from the resolved bounds at compile time (`src/gen/surface/conditions.ts:51-53`), so it moves with the parameter, as it would with a literal.

### 1.4 `recip` and the exact encodings

The default density reads two values that the code computes today (`src/gen/density/defaults.ts:32`, `41`):
- **`1 / clampSigma`** is written `{op: 'recip', x: {op: 'param', path: 'density.noises.jag.clampSigma'}}`. `recip` is a source op whose operand must be a `const` or a `param` (`RECIP_OPERAND` otherwise); a `const` operand must be non-zero with a finite reciprocal, and a `param` operand's static range must exclude 0 (`RECIP_ZERO` otherwise; clampSigma's [1, 8] passes, `detailAmpLo`'s [0, 8] fails). Resolution (§1.6) replaces it by `const(1 / c)`, computed by the same JS `1 / v` on the same double that `C(1 / p.noises.jag.clampSigma)` computes today, so the constant is bit-identical. The noise is still multiplied by the reciprocal, as SP3b §1.1 pins it (`z · (1/cs)` is not `z / cs` in general; master §3.17).
- **`ampHi − ampLo`** is written `{op: 'add', a: {op: 'param', path: 'density.detailAmpHi'}, b: {op: 'neg', x: {op: 'param', path: 'density.detailAmpLo'}}}`. ECMA-262 defines `Number::subtract(x, y)` as `Number::add(x, Number::unaryMinus(y))`, so `hi + (−lo)` equals `hi − lo` for every pair of doubles, ±0 included (also measured on 10^6 random pairs over 40 decades with 0 mismatches, `map-density.md` §6). After folding (§1.6) the node is `const(hi + (−lo))`, the same double the code folds into one constant today.
- `detailAmpLo` itself becomes `{op: 'param', path: 'density.detailAmpLo'}`.

### 1.5 Mutes

- A `tap` accepts `mute?: number | ref` (master §2.5 already types `mute?` on tap). When present, the tap yields the mute value instead of its child. Resolution replaces `{op: 'tap', name, x, mute: m}` by `{op: 'tap', name, x: {op: 'const', v: m}}`: the tap stays (it is still addressable by `tapFn` and `probe`), and the subtree below it leaves the resolved tree (taps inside it become unreachable, so `tapFn` and `probe` refuse them, `src/gen/density/compile.ts:414`). `exprHash` needs no change, since resolved trees carry no `mute`. The inspector still evaluates a node inside a muted subtree, from the source (§3.4).
- A literal `mute` is finite, not −0 (tier 1; `trilerp` of eight −0 gives +0, `map-density.md` §3), |m| ≤ 1e9 (§1.7).
- A mute is an ordinary tree edit: undoable, in the URL and presets, and it affects everything downstream of `terrain`: the T stage (so the cross-section's Voxels mode), the slices and the hover values. The 2D map layers are upstream of `terrain` and never change (Open point 2); the Density tab states this under its plane controls.
- **The toggle's value** (D7) is the neutral value of the tap's parent in the source: 0 under `add`, 1 under `mul`, −1e6 under `max`, 1e6 under `min` (the `islands` convention, master §3.6), and 0 elsewhere (a one-child op, `rangeChoice`, a def's top or the root). Muting `terrain` (under `add`) therefore writes 0; muting `islands` (under `max`) writes −1e6, its default value. The form shows the value and lets the user change it or make it a ref.
- Validation runs on the source tree with mutes ignored (§1.7), so errors and costs inside a muted subtree are still reported and bounded, with their paths.

### 1.6 Resolution and freezing (`src/gen/density/source.ts`, `src/gen/surface/source.ts`)

`resolveDensity(source, params) → DensityExpr` and `resolveRules(source, params) → Rule` first run their tier-2 validator (`validateDensitySource`, `validateRulesSource`, §1.7) and throw `ExprValidationError` / `RuleValidationError` with the issues and their source paths when it fails. Validity is a pure function of the tree (§1.3), so the validator's verdict is memoised in a `WeakMap` keyed by the frozen source object (unfrozen sources are validated on every call; the rules memo requires a deep-frozen tree, which tier 1's clones and the resolvers' outputs are), with a call counter of the misses for the tests: the default costs one validation per process. The resolution itself is not memoised: each call builds a fresh tree, since its numbers depend on the params and a tree shared across contexts would let caches keyed by the resolved tree's identity (such as `densityReferenceOf`, §5.3) serve another seed's noises. Every in-process context (the harness's `ctxFor`, U2's perturbations in `src/metrics/liveness.ts:202-238`, metrics, bench, goldens, presets) therefore gets tier 2 even though it builds params from `applyPatch`/`checkParams` (tier 1 only), and a tier-1-valid `REF_CYCLE` or `VALUE_RANGE` tree is refused instead of overflowing the stack or computing non-finite values (`surfaceProbe.test.ts:111-112` keeps its semantics: an invalid tree throws at context creation). Density, in order:
1. every `param` node becomes `const(value)` and every ref-valued field becomes its number (the q15-normalised leaf value, `kit.ts:193`, or the noise field; `0 − v` for `neg`);
2. every muted tap gets `x: const(mute)` (§1.5);
3. every `recip` becomes `const(1 / c)`;
4. **constant folding**, bottom-up: a node of op `add`, `mul`, `min`, `max`, `neg`, `abs`, `square` or `clamp` whose children are all `const` becomes `const(v)`, with v computed by `src/gen/density/nodes.ts`'s own value functions (`nodes.ts:15-24`), so the folded value is the double the evaluators would compute. `tap`, `interpolated`, `slide`, `rangeChoice` and `ref` are never folded (taps stay addressable, `islands` is `tap(const)`; `interpolated` stays a placement boundary; refs stay refs and a def is folded inside itself).

Rules: every ref-valued field becomes its number (§1.3); nothing else changes.

- **Paths are preserved.** Each step replaces a node in place, so every node that survives resolution keeps its source path; the nodes that do not survive (a muted subtree, a folded subtree's children) are evaluated from the source when the inspector selects them (§3.4).
- **−0.** Folding `neg(param p)` with p = 0, or `neg(const 0)`, yields −0 (`valNeg`, `nodes.ts:19`); the compiler and `exprHash` accept it (`numKey`, `src/gen/density/compile.ts:131-133`), but `canonicalJSON` throws on it (`src/core/params/canonical.ts:28`). Resolved trees are never canonicalised: tests compare them with `exprHash` and a −0-aware deep equality (`Object.is` on every number).
- **Why fold.** It makes the resolved default the very tree the code builds (§2): the default's only all-constant subtrees are the ones the refs introduce. On edited trees folding changes no value; it can remove a position slot (a const never takes one, `src/gen/density/compile.ts:19`), which narrows an early-out interval but never changes solidity.
- **Freeze (D10).** The resolvers build a fresh tree and deep-freeze it. `createDensityContext(ctx, expr = resolveDensity(ctx.params.density.defs, ctx.params))` and `createSurfaceContext(ctx, rules = resolveRules(ctx.params.surface.rules, ctx.params))` pass that frozen tree to the compiler and to the reference, so `dc.expr`, `sc.rules`, `compiled.rules` and `reference.rules` are one frozen object per context. When a caller passes an explicit tree (the `sp3b.density.ops` and `sp3c.surface.ops` goldens, `src/metrics/sp3bGoldens.ts:106`, `src/metrics/sp3cGoldens.ts:127`; about 30 test call sites such as `surfaceProbe.test.ts:37`, `84`, `89`, `147`, `256`, `densityDefaults.test.ts:106`, `250`, `surfaceEstimate.test.ts:25`, `goldens.sp3c.test.ts:117`, `194`), the context **freezes it in place** with `freezeTree` (density) or its twin `freezeRules` (rules, same semantics), a full iterative walk that, unlike `deepFreeze` (`src/core/params/kit.ts:331-337`), does not stop at an already-frozen node and enters only plain objects and arrays. An explicit tree keeps the code-mode validation of compile and reference (`validateExpr`, `validateRules`), not tier 2: explicit trees are code-built. Identity is kept (`interpolatedSlot(e)` and the tests key on source identity, `src/gen/density/compile.ts:106-107`, `436-437`; `densityCompile.test.ts:55`, `265-267`, `325`; `test/metrics/region.metric.ts:152-154`), the values are untouched, and so are the golden sources. This closes SP3c's parked aliasing minor (the surface compiled closures bind fields at compile time, `src/gen/surface/compile.ts:245-318`, while the surface reference reads them at evaluation time, `src/gen/surface/reference.ts:131-138`; mutating `sc.rules` in place made hover and voxels disagree, measured 1,769 of 16,062 voxels, `map-surface.md` §5). A test asserts that mutating `dc.expr` or `sc.rules` (at any depth) throws; a test that mutates a tree after building a context on it now throws too, and the plan lists any such test (none is known at 9fababa). Cloning inside `compileDensity` is rejected for the identity reason above.
- New params mean a new `GenContext` (one per configured epoch, `src/workers/taskHandler.ts:118-146`), so the `surfaceContextOf` WeakMap memo and the surface probe's one-column cache (`src/gen/surface/probe.ts:35-48`) start fresh after every edit; nothing else needs invalidating.

### 1.7 Validation

**Tier 1 — `checkJson` (core, `json.ts`), for both formats.** One budgeted, iterative walk (explicit stack: it never overflows, whatever the input). It counts **every value at every visit** (a container or a primitive; so an in-memory candidate that shares sub-objects or is cyclic hits the count bound instead of looping) and keeps an exact running count of the canonical text in UTF-16 code units (core has no `TextEncoder`, so "128 KiB" is 131,072 characters; tree strings are ASCII). The two whole-value bounds (`JSON_TOO_MANY_VALUES`, `JSON_TOO_LARGE`) stop the walk with that single issue at the value's path, replacing any issue collected so far; the per-value bounds (`JSON_TOO_DEEP`, `ARRAY_TOO_LONG`, `STRING_TOO_LONG`) are reported at the offending value, which is not entered, and the walk goes on (a 100,000-deep chain gives one `JSON_TOO_DEEP`). It stops collecting other issues after 50, appending one `TOO_MANY_ISSUES` issue at the leaf path ("N more"). It checks each object key before writing it into the clone. On success it returns a fresh deep-frozen clone with object keys in sorted order (canonical order, so a tree loaded from a URL and one edited in memory iterate alike, `map-params.md` §7) and registers the clone in a module `WeakSet`; given a value from that set it returns the value itself, unchecked (identity-preserving, §1.12). Rules, each with its code at the offending path (written in the format's path syntax: the density value's JSON path; the rules' path with `root` for the value):

| rule | code |
|---|---|
| values are plain objects (prototype `Object.prototype` or null), arrays without holes, strings, finite numbers or booleans; no `null`, `undefined`, function or other object | `NOT_JSON` |
| numbers finite (`JSON.parse('1e999')` is Infinity) | `NOT_FINITE` |
| no −0 anywhere (`canonicalJSON` throws on it, `src/core/params/canonical.ts:27-28`; it is never normalised, so a typed −0 is reported) | `NEGATIVE_ZERO` |
| every object key matches `^[A-Za-z][A-Za-z0-9_]{0,31}$` (closes empty, dotted and `__proto__` def names, SP3b §13, `map-density.md` §1), checked before the key is written | `BAD_KEY` |
| container depth ≤ 48, the value's top container being 1 | `JSON_TOO_DEEP` |
| ≤ 65,536 values counted per visit; arrays ≤ 1,024 items; strings ≤ 256 UTF-16 units | `JSON_TOO_MANY_VALUES`, `ARRAY_TOO_LONG`, `STRING_TOO_LONG` |
| the canonical text ≤ 128 KiB (the running count stops the walk early; `canonicalJSON` of the clone confirms it) | `JSON_TOO_LARGE` |

Names that are `Object.prototype` members (`constructor`, `toString`, `valueOf`, `hasOwnProperty`, …) match the key pattern and stay valid def and tap names, so **every lookup keyed by tree content** (the ref-target table, def tables, node lookup by path in `source.ts` and `gen/inspect/fieldSlice.ts`, the UI's row caches, the form's per-kind defaults) uses a `Map`, a `Set` or `Object.hasOwn`; today's consumers already do (`expr.ts:144`, `kit.ts:490`, `rules.ts:141-143`).

The depth bound keeps every `canonicalJSON` caller safe: the deepest caller is the lab URL, which nests a B patch (`encodeLabState`, `src/ui/lab/labState.ts:61`, `:100-102`, `:125-130`): the tree's top object sits at depth 4, so a primitive at container depth 48 sits at depth 52 ≤ 64 (`canonical.ts:20`; `map-params.md` §5), 12 levels of margin. A test canonicalises a depth-48 tree through `encodeMapState`, `exportPreset`, `encodeLabState` (B patch), `draftKeyOf` and `stageHashes`. Tier 1 runs inside `checkLeaf`, so `applyPatch`, `checkParams`, `buildSchema` (on the defaults), `importPreset`, `decodeMapState` and the session all get it; nothing downstream can make `canonicalJSON` throw on a json leaf.

**Costs** (`src/gen/inspect/cost.ts`). Three functions, each the only implementation of its cost:
- the **structural cost** of a source subtree: 1 per node plus its children's costs, a `ref` costing its def, `interpolated` costing 1 + 8 × its child (eight corners per voxel), every muted tap counting its child (mutes ignored), additions saturating at 2^31. It is value-independent. The default's root costs 333 (source) and 322 (resolved);
- the **work cost** of an evaluated expression (§5.2), which weights noises by their configured octaves;
- the **column cost** of a tree (below), with every noise at its static maximum weight, value-independent.

**Tier 2 — `validateDensitySource` (gen).** On the tier-1 clone, collecting every issue (at most 50, as tier 1), never throwing:
1. per-node structure, recursive within one tree (depth ≤ 48 by tier 1): `validateExpr`'s checks (`expr.ts:133-286`: ops, keys, fields, noises, names, `CLAMP_ORDER`, `RANGE_ORDER`, `KNOTS_*`, `DUPLICATE_TAP`, …) extended by a `source` mode that accepts `param`, `recip`, `tap.mute` and ref-valued fields, with the order checks over static ranges (§1.3); plus `UNKNOWN_PARAM` (a path not in the targets), `RECIP_OPERAND`, `RECIP_ZERO` (density has no int field, so no `PARAM_KIND`, §1.3); tap names match the key pattern (`BAD_NAME`); literals (`const.v`, `clamp`/`rangeChoice` bounds, knot coordinates, `mute`) have |v| ≤ 1e9 (`LITERAL_RANGE`; the master's cave formulas use ±1e9 and ±1e6, master §3.6); every `slide` segment's `v1 − vk` and `(v1 − vk) / (y1 − yk)`, computed as `slideAt` does (`nodes.ts:30-41`) on the range endpoints that maximise them, are finite (`SLIDE_SLOPE`; SP3b §13; measured NaN for knots `[[0, −1e308], [1, 1e308]]`, `map-density.md` §2);
2. counts: ≤ 4,096 nodes (`TOO_MANY_NODES`, at the leaf path) and ≤ 64 defs (`TOO_MANY_DEFS`, at `defs`);
3. the def graph, by an iterative walk: `UNKNOWN_REF`, `REF_CYCLE`. The root's refs get their own bucket (the empty-name bug, `expr.ts:146-147`, `224-226`, is fixed in `validateExpr` itself; the key pattern also forbids empty names);
4. in topological order of the def graph (no recursion through refs), for **every tree root: `root` and each def, reachable or not**, with mutes ignored: the **expanded depth** (depth counting through refs, a `ref` one level above its def's top node) ≤ 128 (`EXPANDED_TOO_DEEP`, at the deepest node of that root's own structure, a ref standing for its def's expansion, so each refused root names a node of its own) and the structural cost ≤ 65,536 (`TOO_COSTLY`, at that root's path, message with the cost). Since a node's subtree is part of its tree root's, every node the inspector can select, an unreachable def's or a muted subtree's included, is bounded. These bound what recurses through refs (the compiler, the reference, `exprHash`, the bounds, all measured to overflow beyond about 1,800-4,200 nested nodes on Node, `map-density.md` §1) and the reference's cost, which grows with the expanded tree (`src/gen/density/reference.ts:84`, `107`; measured exponential with shared defs, `map-workers.md` §6): 60 defs `dᵢ = add(ref dᵢ₋₁, ref dᵢ₋₁)` reachable from nothing are refused at `defs.d<k>`;
5. only then the checks that walk through refs (`NESTED_INTERPOLATED`), the **static magnitude analysis** (§1.9; one `VALUE_RANGE` issue, at the first node whose static interval leaves ±1e100 in source post-order (children before parents) over `root` then each def, so it names the node whose own op leaves the range), and the **column cost** (`COLUMN_COST`, at the leaf path): the nodes of the source structure with mutes applied and refs expanded (no value is read), each noise weighted at its static maximum (16 octaves, double), every voxel-placement node counted 98,304 times (a chunk column) and every node under `interpolated` 1,225 times (25 × 49 quart corners), must not exceed `DENSITY_COLUMN_COST_MAX` = 64 × the default tree's column cost (`core/constants.ts`). The measured worst valid trees of the first draft (2,852 and 6,693 ms per compiled column, against 4.4 ms for the default, `spec-review-security.md`) are refused by it; the T stage, the Voxels slice and the probes thus stay within a known factor of today.

**Tier 2 — `validateRulesSource` (gen).** `validateRules` (`src/gen/surface/rules.ts:175-319`; depth ≤ 32 as `TOO_DEEP`, ≤ 4,096 nodes as `TOO_MANY_NODES`, unchanged) extended by the ref form (`UNKNOWN_PARAM`, `PARAM_KIND` for a non-`int` target in an int field, `BAD_FIELD` for a malformed ref, all at the field's path) with every value check over the ref's static range (`OUT_OF_RANGE` for an int field, `RANGE_ORDER`, `GRADIENT_ORDER`, as §1.3), literals |v| ≤ 1e9 in the four number fields (`LITERAL_RANGE`; int-field literals keep `OUT_OF_RANGE` [−384, 384]), `biome.biomes` ≤ 64 entries (`TOO_MANY_BIOMES`, at `<id>.if….biomes`, its entries then not checked; a 200,000-entry list validates today, `map-surface.md` §1), the **column cost** (`COLUMN_COST`, at the leaf path, judged only on a tree with no other issue: the rule node count times the voxels a column evaluates, 98,304 without a fast path or 256 × (1 + the fast path's largest depth bound, with each ref at the end of its static range that maximises it, SP3c §3.4) with one, at most `RULES_COLUMN_COST_MAX` = 64 × the default's), and **`NOT_SOLID`**: a `block` whose state does not collide (`COLLIDE[state] === COLLIDE_NONE`, `src/world/blocks/kinds.ts:55-58`; today only `air`). The T stage derives `oceanFloorWG` from solidity on the assumption that every surface state collides (`src/gen/pipeline/terrainStage.ts:138-143`; SP3a §3.4's `OCEAN_FLOOR_WG = COLLIDE ≠ none`, `WORLD_SURFACE_WG = state ≠ air or fluid`), so a non-colliding rule result would make both heightmaps disagree with the stored states. (The surface probe's solidity check reads the density's solidity, `src/gen/surface/probe.ts:62`, and would report the non-colliding state at a density-solid voxel.) `bandlands` yields terracottas only, which collide. `NOT_SOLID` is in `validateRulesSource` only, the path by which an edited tree reaches the T stage, so `validateRules` and the tests that use `air` in code-built trees (`surfaceRules.test.ts:65`, `72`, `88`; `surfaceReference.test.ts:159-177`; `surfaceCompile.test.ts:41`) are unchanged; future non-cube colliding states (`boxes`) pass it.

**The two column-cost maxima** are computed by the plan's first density task from the formulas above and pinned in `core/constants.ts`, with a test that recomputes `64 ×` the default's cost for each; the task records in this spec the default's two costs and the ratio of a default-sized rule tree without a fast path (expected well inside 64 ×). If the bound would refuse a default, a U2 variant, a uiSmoke tree or a default-sized rule tree without a fast path, the plan stops and the spec is amended. Recorded by that task (`gen/inspect/cost.ts`, `test/unit/inspectCost.test.ts`): the default density tree's column cost is 14,907,917 (148 units × 98,304 at voxel placement, the `detail` noise weighing 128, plus 293 × 1,225 under `interpolated`), so `DENSITY_COLUMN_COST_MAX` = 954,106,688; the default rule tree's is 2,169,856 (163 nodes × 256 × (1 + 51): its largest depth bound is a floor `stoneDepth` offset 4 plus SD_MAX's static maximum ⌊3.25 + 2.75 · 2 · 8⌋ = 47), so `RULES_COLUMN_COST_MAX` = 138,870,784; a default-sized rule tree without a fast path costs 163 × 98,304 = 16,023,552, 384 / 52 ≈ 7.4 × the default's. The U2 variants (terrain muted: 14,548,992; the gradient at 12: unchanged) and the uiSmoke trees (islands −10: unchanged; terrain muted) are within both maxima.

**Issue codes** are pinned by path and code: every test asserts exact `(path, code)` pairs. Tier 1's codes are `NOT_JSON`, `NOT_FINITE`, `NEGATIVE_ZERO`, `BAD_KEY`, `JSON_TOO_DEEP`, `JSON_TOO_MANY_VALUES`, `ARRAY_TOO_LONG`, `STRING_TOO_LONG`, `JSON_TOO_LARGE`, `TOO_MANY_ISSUES`; no code names two different bounds.

`−0` stays valid in code-built density trees (`validateExpr` accepts it, pinned by `densityExpr.test.ts:89`); only json leaves (tier 1) reject it. Tree literals are not q15-quantised (`canonicalJSON` prints `String(v)`, a lossless round trip); only the parameter values that refs read are.

### 1.8 Where validation runs, and rejection (D2)

`validateParamTrees(params): Issue[]` (`src/gen/trees.ts`) runs both tier-2 validators on a params document and prefixes each issue with its leaf path (an empty node path gives the leaf path alone, §1.2). Both validators are memoised by tree identity (§1.6), so a call on a document whose trees are unchanged costs two `WeakMap` lookups. It runs:
- **in the session:** `WorldSession`'s constructor init (`src/engine/session.ts:119`) gains `validateParams?: (params: Params) => readonly Issue[]`, run at every place that produces params:
  - the **constructor**, after its `applyPatch` of the initial patch succeeds (`session.ts:126-136`): issues take the existing invalid-patch branch, so the session opens the default profile with no changes and `initNotice` names the first issue (`invalid patch (<path> <code>); opened the default profile with no changes`). This is how a fresh tab opens a `?map#` link (`src/ui/map/mapPage.ts:47-49`; `decodeMapState` checks tier 1 only, `src/ui/map/mapState.ts:55`), so a crafted or older link with a semantically invalid tree opens the defaults with a notice instead of a pool that answers `BAD_PARAMS` forever;
  - **`setProfile`** (`session.ts:218-224`), on the profile's params: issues refuse the switch (`{ok: false, issues}`); SP3e's overlays may hold whole trees (§13);
  - **`commitPatch`** and **`load`**, after `applyPatch` succeeds: issues make the change fail exactly like an out-of-range value, `{ok: false, issues}` and nothing changes (`session.ts:275-280`), so the world keeps the last valid tree and the editor shows the error;
  - **`restore`** (`session.ts:319-327`): every snapshot passed the hook when it was recorded and validity is a pure function of the tree, so a failure is a bug, and `restore` throws as it does today for an `applyPatch` failure.
  Every page that creates a `WorldSession` passes `validateParamTrees` (`ui/` may value-import gen, `imports.ts:32`); an arch test greps every `new WorldSession(` under `src/ui/` for `validateParams`. The option stays optional for the engine's own tests. Unit tests: the constructor with a tier-2-invalid patch (`density.defs.root.b.x = {op: 'bogus'}`) opens the defaults with the notice `invalid patch (density.defs.root.b.x UNKNOWN_OP) …`, and with a valid edited tree opens it; `setProfile` refuses an invalid profile; a slider-only commit does not re-run either validator (a call counter on the memo misses).
- **in the worker:** configure runs `checkParams` and then `validateParamTrees`, and replies `BAD_PARAMS` with the first 5 issues (`src/workers/taskHandler.ts:134-135`), so an invalid tree can never become an `INTERNAL` error inside a job's lazy compile (`map-workers.md` §2). With the constructor hook, the session never sends one, so this is a guard against bugs;
- **in the editors**, as you type (§3.5), with the same function;
- **in the resolvers** (§1.6), for every in-process caller.
- URL and preset loads reach the session through `session.load` (a `hashchange`, `mapState.ts:96-104`; the presets tab's import) or the constructor (the page's first hash), so a semantically invalid tree in a link or a file is refused with its paths, like any invalid value (the map notice prints `path code`, `mapState.ts:56`, `103`). A `hashchange` keeps SP2b's order (the hash's view is applied, then `load` refuses the draft), so the view moves while the draft, the history and the URL's tree stay (the page rewrites the address bar to the current draft at that view). The page builds its session through the pure `openMapSession(decoded, random)` (`src/ui/map/mapState.ts`), the only `new WorldSession(` under `src/ui/`.
- The lab page's URL (`src/ui/lab/labState.ts:66`, `:112`) accepts tier-1-only trees; the lab never generates terrain, so this is harmless and stays so.

**The default trees pass both tiers.** An invariant with its unit test: `validateParamTrees(resolveProfile(p))` is `[]` for every profile of `PROFILES` (`resolveProfile` is tier 1 only, `src/core/params/profiles.ts:36-40`), and the two U2 variants (§7), the uiSmoke trees (§6) and every DT2 edited tree that is kept pass both tiers.

### 1.9 NaN-free values and sound bounds (D8)

Two measures, each closing a different gap.
- **Static (S): no NaN or ±∞ on a valid tree.** The master requires NaN-free generator outputs (master §3.17, line 862). Tier 2's magnitude analysis evaluates, once per node with a per-def memo, an interval of the node's possible values with the interval functions of `nodes.ts`, for every node of `root` and of every def (reachable or not), from: `y` ∈ [−64, 320] (corners reach `cornerY(48)` = 320, `nodes.ts:98`); `noise` and `noise2` ∈ [−8, 8] (clampSigma's static maximum); `const` exact; `param` and ref-valued fields their static ranges; `recip` as §1.4; a muted tap the hull of its mute and its child's interval (so the node is bounded both as the tree evaluates it and as the inspector evaluates it, §3.4); and every `col` field its entry of **`COL_FIELD_BOUNDS`** (`core/constants.ts`). A tree is rejected (`VALUE_RANGE`) when any node's interval leaves ±1e100; with literals ≤ 1e9 that leaves astronomical headroom under the largest double for `lerp`'s `b − a` and the interval widening.
  - `COL_FIELD_BOUNDS` is the artefact of the plan's first density task: for each of the 19 `SAMPLE_FIELDS` (`src/gen/column/columnStage.ts:32-35`) a closed interval proven from its formula in `src/gen/column/` for every schema-valid params document, with the argument written beside it. A field without a proven bound has the interval [−∞, ∞], so a `col` read of it is `VALUE_RANGE` wherever it is read (for example `riverDist = |Rz| / max(gradLen, 1e-4)`, `src/gen/column/rivers.ts:48`, if |Rz| is unbounded). The task bounds the four fields the default reads (`offset`, `jag`, `sigma`, `E`) first; **if one of them cannot be bounded, the plan stops and this spec is amended** (the default would otherwise be refused).
  - A unit test asserts that the sampled values of every field over the DT2 columns lie inside their `COL_FIELD_BOUNDS` entries, and that both default trees pass `VALUE_RANGE` (§1.8's invariant).
- **Dynamic (D): sound early-outs whatever happens.** The interval ops pick endpoints with `<` and `>`, so a NaN endpoint is dropped (`ivMul`, `ivMin`, `ivMax`, `ivHull`, `ivAbs`, `ivSlideFactor`, the slot hulls; `nodes.ts:139-232`, `src/gen/density/bounds.ts:148-207`), and infinities without NaN already break soundness (a tree that validates today makes `fillDensityColumn` mark a cell solid while the probe says air, `map-density.md` §2). Every interval op of `nodes.ts` returns **UNKNOWN** = [−∞, +∞] when an input endpoint is non-finite or a result endpoint is NaN, explicitly (a test, not a comparison), and an op with an UNKNOWN input is UNKNOWN; `clamp` and `rangeChoice` never turn UNKNOWN into a known interval. The hulls of `bounds.ts` seed `lo = Infinity`, `hi = −Infinity` (`bounds.ts:163`): they test `isNaN` on **each value** they fold in and the finiteness of the **finished** hull, never of the sentinel, so a hull of finite values is exactly today's (a naive check on the sentinel would make every position slot UNKNOWN and change the masks without changing a golden). `fillDensityColumn` already treats a root interval it cannot decide as undecided and evaluates the voxels (`bounds.ts:267`, `271`), so an UNKNOWN root is evaluated. With finite intervals (every default world) D changes nothing; this is proven, not only claimed: a unit test hashes `fillDensityColumn`'s mask and solid arrays over 32 seed-'42' columns and compares with the value recorded at 9fababa, and §11's exit row compares the region metrics' outputs exactly. This is SP3b §13's "make the interval ops propagate NaN, or widen a NaN endpoint to [−∞, ∞]", applied to infinities too.

### 1.10 The fast-path depth contract (D11)

SP3c's fast path is correct only if every position's surfaceDepth ≤ SD_MAX (`src/gen/surface/compile.ts:334`, `391-399`). Two cheap guards close the cases the code allows (`map-surface.md` §6, measured 25,175 and 2,012 wrong voxels):
- `scanColumn` clamps Ns to ±the depth noise's clampSigma before using it (`src/gen/surface/scan.ts:196`). `NormalNoise.z2` already clamps to ±clampSigma (`src/core/noise/normal.ts:32-37`), so this is bit-identical for schema noises and only protects injected test noises;
- `surfaceScanSettings` (`scan.ts:116-124`) throws a RangeError for a `depthMul` that is negative or non-finite (the schema's [0, 2], `schema.ts:124`, never produces one).
A test compares fast and full `fillColumn` for both cases and asserts surfaceDepth ≤ SD_MAX on sampled columns.

### 1.12 URL, preset and history size (D13)

Atomic diffs put a whole edited tree in the patch: one threshold change puts the 6.8 KB rule tree in the URL, the preset, the patch box and the history snapshot (measured: map URL 2,123 characters with the density tree edited, 11,221 with both, `map-params.md` §5). This is accepted, with four measures so its cost stays bounded:
- **Identity-preserving validation.** `commitPatch` re-applies the whole patch on every edit (`session.ts:268-277`), and `applyPatch` runs `checkLeaf` on every leaf the patch names (`kit.ts:437-441`). Tier 1 returns a frozen value it produced unchanged (§1.7), tier 2 is memoised by identity (§1.6), and `diffParams` returns the base object when an atomic leaf is the same object (`kit.ts:472`), so an edited tree is cloned and validated once, when it is set, and every later snapshot shares it by reference. A session test asserts that two slider edits keep the same `density.defs` object in the state and in both history snapshots.
- **Canonical text cache.** `canonicalJSON` caches the text of the frozen values in tier 1's registry (a `WeakMap`), so `draftKeyOf`, `paramsHash` and `stageHashes` reprint an unchanged tree in O(1). Each hash still reads the whole text (a slider commit hashes about 270 K characters twice, `paramsHash` for the epoch and `draftKeyOf`), so `fnv1a64` (`src/core/hash.ts`) hashes the string's UTF-8 bytes streamed from the string instead of building `utf8Bytes`' array first: the same values (lone surrogates as EF BF BD, as before; goldens unchanged), about 1.6 ms instead of 5.3 ms per 270 K characters, which keeps a commit with two capped trees at about 3.2 ms p50 (§9).
- **History keys.** `HistoryEntry.key` (`session.ts:48-51`, `305-307`) becomes `fnv1a64` of the draft's canonical text instead of the text itself (up to about 256 KiB per entry with two capped trees, × 101 entries); the cursor's comparison uses the hash. The history then holds at most 101 snapshots (`session.ts:46`) sharing their trees.
- **URL cap.** `writeUrl` measures the encoded hash; above `URL_HASH_MAX` = 64 KiB it does not write it (the address bar keeps the last state that fit, `src/ui/common/urlWriter.ts:18-22`, which today swallows a throwing `replaceState` and retries every second) and shows a persistent warning, "The edited trees are too large for the URL; export a preset to share them", until the state fits again. On read, `decodeMapState` refuses a hash longer than 1 MiB before `base64urlDecode` (`mapState.ts:66-82`). uiSmoke records the URL length after its edits (§6).
A finer diff inside json leaves would change `merge` semantics and is not built. A bench row `session.commitMaxTree` (§9) pins the cost of a slider commit with two trees at the 128 KiB cap.

### 3.1 Placement and layout

- `DrawerTabId` gains `'density'`, appended last in `DRAWER_TAB_IDS` with the label "Density" (`src/ui/map/layout.ts:15-17`), so the tab keys keep their order and the uiSmoke tabs step (Cross-section ← → Spline) stays valid (`test/tools/uiSmoke.ts:831-837`). - The tab body is a grid `220px | 280px | minmax(0, 1fr) | minmax(0, 1.2fr)`: **tree | node form | JSON editor | slice viewer**. Below 1,200 px of drawer width the last two columns become one with two sub-tabs, "Slice" (shown first) and "JSON". Below 900 px the columns stack (tree, then form, then the Slice/JSON sub-tabs), as the spline drawer stacks (`src/ui/splineEditor/drawer.css:72-79`). The drawer's height is the shared one (300 px by default, up to 60 % of the viewport, as low as 160 px; `layout.ts:23-35`, `map.css:34`); the slice canvas keeps a minimum of 128 × 128 CSS pixels and the drawer scrolls below that.
- **State across tab switches.** Hidden drawer tabs keep their DOM (`hidden` attribute, `layout.ts:309`), so selection, expansion and the JSON buffer survive a switch. The scroll offsets of the tree, the form and the textarea are saved when the tab is hidden and restored when it is shown (whether the browser keeps `scrollTop` across `display: none` is not relied on, `map-ui.md` §2). The JSON text's scroll is **owed** while the text is not displayed (the drawer tab, the JSON sub-tab or a layout change hides it, and a hidden textarea ignores scroll writes): a scroll asked for then — a row selected, an issue clicked, a re-print — is written when the text shows again, the latest winning, and replaces the offsets saved at the hide; so below 1,200 px a row selected under "Slice" is in view when "JSON" is shown, and a re-print while the tab is hidden shows the anchor it mapped. Nothing is persisted across reloads (the layout stores no drawer tab, `layout.ts:160`).
- The same preset export/import, share URL, undo/redo and reset carry the edited trees: they are ordinary leaves of the session.
- A one-line note under the plane controls: "Tree edits show in the slices, the Voxels mode and the hover values; the 2D map is upstream of the terrain" (§1.5).

### 3.2 Tree

- Two roots: **Density** (`root`, then each def `defs.<name>` in key order) and **Surface rules** (`root`). A row shows the node's path tail, its op or kind and a short summary: `const 0.5`, `param density.detailAmpLo = 0.6`, `recip`, `noise overhang`, `col offset`, `slide 4 knots`, `tap terrain`, `ref base`; `sequence 3`, `if biome(desert, beach, …) → sand`, `if stoneDepth floor 0+sd`, `block grass_block`, `bandlands`. Conditions are rows of their rule (`.if`, `.if.if`). A row's `title` holds its full path.
- A tap row carries its mute toggle; a muted tap shows its value and its subtree dimmed. Toggling it from the row is a plain edit: the selection stays where it was (the form's own mute acts on the selected tap, which stays selected), so the selected node's slice and hover value show the muted world.
- Rows are expandable; the initial expansion is three levels, and an "Expand to selection" button opens the selected node's ancestors. Indentation is 8 px per level, capped at 12 levels (the default density tree is 17 levels deep down to the `clampSigma` param, which at 12 px per level left no room in 220 px). The pure model (`ui/inspector/model.ts`) builds the rows from the session's current values; the DOM re-renders only when a key string changes (the spline drawer's precedent, `src/ui/splineEditor/tree.ts:16-42`). The column widths are fixed in SP3d (resizable columns are SP10 polish).
- **Selection** is (root, node path). After undo, redo, reset, load or a form edit that renumbers siblings, the selection follows the longest prefix of its path that still names a node (`followNode`, `src/ui/splineEditor/model.ts:368-382`).
- **Highlighting.** Selecting a row highlights the node's text range in the JSON editor (§3.5) and scrolls the text to it. Moving the caret in the editor selects the innermost node whose range contains it only while the buffer is clean or parses (debounced at 150 ms with the validation) and the path exists in the session's tree; a path that exists only in the typed buffer moves the editor's highlight, not the tree's selection, so typing never sends slice or probe requests for nodes the session does not have.

### 3.3 Node form

One field per scalar of the selected node: `const.v`, `clamp`/`rangeChoice` `lo`/`hi`, `slide` knots (a two-column table with add and remove), noise ids (a select of the schema's noises of the right dims), `col.field` (a select of `SAMPLE_FIELDS`), tap name and mute, def and ref names; for rules every field of `FIELDS` (`src/gen/surface/rules.ts:134-139`, exported; field names only): biome list, block state (a select of the colliding registry states), `side`, booleans and the numeric fields. Fields commit on `change` (Enter or blur; Escape restores; a refusal keeps the text red with the issue lines under it), as `valueField` does (`src/ui/paramPanel/controls.ts:102-149`). A typed literal is read as the panel reads it (`parseFieldText`): the number its trimmed text spells (`Number`'s reading, so `0x10` is 16), a typed −0 written 0 (the panel's q15 stores −0 as 0); text that spells no number (`0,5`, an empty field) is refused with `NOT_NUMBER` naming what was typed (`expected a number, got "0,5"`), as the panel refuses it; a non-finite number is tier 1's `NOT_FINITE`. Slide knots are sorted by y when the table commits, so editing one cell never hits `KNOTS_ORDER` mid-edit.

Every edit is a pure operation on the tree (`ui/inspector/form.ts`) that yields a candidate tree, then one `session.set('<leaf>', candidate)` through the page's `edit` wrapper (`mapPage.ts:83-89`): one undo step, the URL, the live preview. The session's refusal is shown as the issue lines and the selection is restored (the spline drawer's commit pattern, `drawer.ts:287-320`). Node-level paths are never session paths (`session.set` accepts schema paths only, `session.ts:60-64`).

Operations:
- **Param ref** (D4). Every numeric field has a select "literal / <compatible targets>", each target listed with its current value, and, outside `const.v`, a "negate" checkbox. On `const.v` choosing a target replaces the `const` node by `{op: 'param', path}`, and "literal" replaces a `param` node by `const(<its current value>)`; on any other numeric field (density's `clamp`/`rangeChoice` bounds, knot coordinates and `mute`, and the rules' nine fields) it writes the ref form `{param, neg?}`, and "literal" writes the current resolved value. An int field lists only `int` targets. While a field is a ref the form shows the target's slider (the parameter panel's row, `controls.ts:168-219`); moving it sets the **target leaf** (`session.set(targetPath, v)`), exactly as the Parameters tab does; a noise's `clampSigma`, which is not a schema leaf, is written as the partial noise `{clampSigma: v}` on its noise leaf (`session.set` accepts schema paths only).
- **Replace op / kind.** A select of the ops (density: every source op; rules: every rule kind for a rule node, every condition kind for a condition); options that cannot validate are disabled (`ref` while `defs` is empty, the default; `recip` over a child that is not a `const` or `param`). Children are kept **by position**: the new op's child slots, in `SOURCE_CHILD_KEYS` order (`EXPR_CHILD_KEYS`, `src/gen/density/expr.ts:56-61`, plus `recip: ['x']` and `param: []`), take the old node's children in their evaluation order; missing slots get `const 0` (`recip`'s gets `const 1`); extra children are dropped. Missing scalars take the op's defaults, which live in `ui/inspector/form.ts` (numbers may not be exported from gen): `const` 0; `clamp` 0 … 1; `rangeChoice` 0 … 1; `slide` knots `[[-64, 0], [320, 1]]`; `noise`/`noise2` the first schema noise of its dims; `col` `offset`; `tap` a fresh name `tap<k>` (the smallest unused k ≥ 1); `ref` the first def in key order; `param` the first target. Rules: `sequence` ↔ `condition` keeps the child (`rules: [then]` / `then: rules[0]` or an empty sequence) with `if: skyOpen`; `block` defaults to `stone`; condition defaults are `biome{[plains]}`, `stoneDepth{floor, 0, false}`, `water{0, false}`, `yAbove{63, false}`, `verticalGradient{0, 8}`, `steep{1}`, `noiseThreshold{surface.noises.patch, 0, 8}`, `temperatureBelow{0}`, and `not{<the old condition>}`.
- **Wrap.** Density: wrap in a `tap` with a fresh name. Rules: wrap a rule in a one-child `sequence` (same result).
- **Delete.** Density: a node with one child slot (`neg`, `abs`, `square`, `clamp`, `slide`, `interpolated`, `tap`, `recip`) is unwrapped (replaced by its child); any other node is replaced by `const 0`; a def is removed (refused with `UNKNOWN_REF` if referenced). Rules: a child of a `sequence` is removed (later siblings renumber; the selection follows, §3.2); the root or a `then` becomes an empty `sequence` (yields nothing); a `not` is unwrapped; other conditions can only be replaced.
- **Add.** "Add def" (`def<k>` = `const 0`); "Add rule" appends `block stone` to a selected `sequence`.
- **Rename def.** One edit that renames the def and every `ref` to it (renaming only the def would leave `UNKNOWN_REF`).
- **Mute** (density taps): the toggle of §1.5.
- **Reset node** is not offered; "Reset" on the JSON editor resets the whole leaf (§3.5).

The form also shows the selected node's **value at the hovered voxel** (§3.6) and, for the tree as a whole, two lints (warnings, never refusals; the hard bounds are §1.7's): "no fast path: every solid voxel is evaluated" when the resolved rules have none (SP3c §3.4; up to 4,096 nodes per voxel in the worst case, `map-surface.md` §4), and "density cost ≈ N × the default" when the root's work cost exceeds 4 × the default's.

### 3.4 Selected-node semantics

The value of a density node at a voxel is the reference evaluator's value of the node's **source subtree, resolved on its own**: `resolveDensityNode(source, path, params)` applies §1.6 to the subtree at `path` of `params.density.defs` with the tree's resolved defs. Mutes strictly inside the subtree apply; the node's own mute (a selected muted tap shows its subtree's value, which is what the user wants to see when deciding whether to unmute it) and its ancestors' mutes do not. The subtree is taken from the source, never from the resolved tree, because resolution drops the subtree under a muted tap and the children of a folded node (§1.6): a node under the muted `terrain` tap, the brief's main use case, is evaluated like any other. The UI and the worker call the same function, so they agree on the expression and its cost (§5.2). Placement:
- a node with an `interpolated` ancestor in its tree is evaluated as `{op: 'interpolated', x: node}` at voxel placement, as the reference does for an inside tap (`src/gen/density/reference.ts:122-126`); evaluated bare it would give the corner placement's number (`reference.ts:6-11`);
- a def, and a node inside it, takes the placement of the def's first reference in source DFS order (root first, then defs in key order), the rule `findTap` uses (`reference.ts:153-161`); an unreachable def is evaluated at voxel placement;
- the root is the final density, the resolved tree's `voxel` value (this takes precedence over the own-mute rule: a muted root tap shows its mute value).
The expression carries only the resolved defs the node reaches (transitively), so a node inside a def does not duplicate the def's taps (`DUPLICATE_TAP`). A rule node's "value" is a mask (§4.1).

### 3.5 JSON editor

- A `wrap="off"` textarea over a mirror `<pre>` backdrop with the same font, size and padding (`ui/inspector/jsonEditor.ts`): the backdrop paints the highlighted node range (a textarea cannot paint a range while unfocused, and focusing it would steal focus from the tree row), and the editor scrolls a range into view by its line index × the line height. The text is the whole tree of the selected root (density or rules), printed by `printTree` (`ui/inspector/jsonText.ts`): two-space indentation; in each object `op` (or `kind`) first, then the scalar fields in their table order, then the children in evaluation order; `defs` keys sorted; a node without child nodes, and a number array (knots), on one line. `canonicalJSON`'s sorted keys (`op` last, `map-ui.md` §9) are not used for display.
- `parseTree` is an iterative JSON parser that returns the value, the text range of every node path, and syntax errors with their line and column (`JSON.parse` gives no offsets). It defines object keys with `Object.defineProperty` on a null-prototype object and then normalises to a plain object, so a `"__proto__"` key reaches tier 1 and is reported as `BAD_KEY` instead of being dropped; a **duplicate key** is a syntax error at its position. The printer records the same ranges, so highlighting works on both printed and typed text. A buffer over 512 KiB is not parsed ("too large to validate").
- **Validate as you type** (150 ms debounce), without applying: parse, then tier 1 and tier 2 (the same `checkJson` and `validateParamTrees` functions the session uses), then the issues, one per line as `<node path>: CODE — message` (the leaf prefix removed; at most 50 lines and a "N more" line, §1.7). Clicking an issue selects its node and scrolls the text to it.
- **Apply** (and Ctrl+Enter) sends the parsed tree with one `session.set('<leaf>', value)`; an invalid tree is never sent, and if the session still refuses (it validates again) its issues are shown. **Reset** is `session.reset('<leaf>')`: the profile's tree (`session.ts:236-240`; the default for every profile ready in SP3d). After a successful Apply or Reset the editor re-prints the session's tree into the buffer and marks it clean, restoring the scroll and the caret on the same node path. **Escape** reverts the buffer to the current tree: the shortcut layer already leaves Escape to text-entry controls (`src/ui/common/keys.ts:25-35`), so the editor's own handler reverts the buffer and the drawer stays open. Ctrl+Z inside the textarea is the browser's text undo, as for every text entry.
- **Dirty-buffer rule.** The buffer is replaced by the current tree only when that leaf's value changes **from elsewhere** (an undo, a form edit, a preset load) and the buffer is clean (equal to the last printed text); a re-print restores scroll and caret by node path. If the buffer is dirty then, it is kept and a notice offers "Revert to the current tree". Changes to other leaves never touch it (unlike the presets patch box, which overwrites typed text on any patch change, `presetsTab.ts:165-211`).
- The buffer, the dirty rule, the debounce (with an injected clock) and Apply / Reset / Escape are the pure `ui/inspector/editorModel.ts`; `jsonEditor.ts` only binds it to the DOM.

## 4. Slice viewer

### 4.1 Fields

The field select offers **density**, **selected** and **blocks**. `selected` follows the tree's selection: a density node gives the `node` field, a rule node or condition the `rule` field; it is disabled, with a note, for a rule node on a horizontal plane. Selecting a node never changes the field.

| field | planes | value per sample |
|---|---|---|
| `density` | vertical, horizontal | the final density: the resolved tree's root, by the reference evaluator |
| `node` (selected, a density node) | vertical, horizontal | the selected node's value (§3.4), by the reference evaluator |
| `blocks` | vertical | the stored state and fluid of the voxel after the T stage (as the Voxels mode) |
| `rule` (selected, a rule node) | vertical | on a density-solid voxel: 1 when the voxel's rule path (the reference walk, as `surfaceProbe`) passes through the selected rule, or, for a selected condition (`<ruleId>.if…`), when that condition holds at the voxel; else 0. On air and water voxels (no run, so no `{scan, p, y, r}` for `holds`, `src/gen/surface/reference.ts:125-138`) and at the bedrock row y −64 (which the rules never evaluate; only a probe can ask for it): n/a (`SLICE_RULE_NA` = 255), drawn grey and left out of the share |

- All density fields use the reference evaluator, the root included, so a slice shows exactly what the hover probe gives at the same voxel (DT2 proves the compiled closures equal it, `test/metrics/region.metric.ts:216-234`); the reference is about 2.7 × slower than the closures (`map-workers.md` §7), within the budget (§9).
- The surface reference gains `nodeAt(id)` and `conditionHolds(id, scan, set, p, y)` (the scan settings, as `evaluate(scan, set, p, y)` takes them: a `temperatureBelow` condition reads their lapse and lapseBase; it already has the per-condition `holds`, `reference.ts:131-138`, and identity-keyed prep maps over its own frozen tree). Rule fields need the column's scan (density fill, water v0, biome buffer), which only vertical planes can afford; blocks need whole T columns. A horizontal plane offers `density` and `node` only (a horizontal block slice would need thousands of full columns).

### 4.2 Planes and samples (`src/gen/inspect/fieldSlice.ts`)

- **Vertical:** along the cross-section's line A → B (any orientation; master §5.5's XY@z and ZY@x are its axis-aligned cases), y −64 … 319, with the sea-level line at 63. Sample (i, r), i, r ∈ 0 … n−1: the voxel (⌊xᵢ⌋, y_r, ⌊zᵢ⌋), with (xᵢ, zᵢ) = `segmentPointAt(segment, i, n)` (`src/metrics/crossSection.ts:70-75`, generalised to t = i/(n−1), its default n = 512 keeping every existing caller) and `y_r = 319 − ⌊(2r + 1) · 384 / (2n)⌋` (row centres: 318 … −63 at n = 128, 313 … −59 at n = 32). The segment rules are `segmentProblem`'s (`crossSection.ts:51-57`). The y control draws its level as a line across the vertical slice.
- **Horizontal:** XZ at y (integer, −64 … 319; 63 by default), centred on (cx, cz) (integers; the map view's centre until a map click sets it, §3.7), extent E ∈ {256, 512, 1024, 2048, 4096, 8192} blocks (a select; 2048 by default). Sample (i, j): `x_i = cx − E/2 + ⌊(2i + 1) · E / (2n)⌋`, `z_j` alike (integers for every allowed E and n). The square must lie inside the world window: `cx − E/2 ≥ −2^19` and `cx + E/2 ≤ 2^19` (and for z); the UI clamps the centre, the worker refuses otherwise.
- **Resolution:** n = 128 (16,384 samples); on a change, first a draft at n = 32 (§4.5). The sizes and extents are `SLICE_NS` and `SLICE_EXTENTS` in `core/constants.ts`.
- The UI's hover, the worker and the pool use these functions from `gen/inspect/fieldSlice.ts`, so a pixel always names the voxel that was evaluated. gen cannot import `metrics/` (`test/arch/rules/imports.ts:17`), so `segmentPointAt` stays in `metrics/crossSection.ts` and the vertical geometry takes the sample columns' points as input (`pointAt(i)`): the worker (`fieldSliceJob.ts`) and the UI compute them with `segmentPointAt` and check the segment with `segmentProblem`; `fieldSlice.ts` owns `y_r`, the voxel floor, `x_i`/`z_j` and the square check (with `core/coords.ts`'s `WINDOW_HALF`), and refuses a bad geometry with a `RangeError` whose text is the worker's `BAD_ARGS` message.

### 4.3 Drawing (`ui/inspector/sliceModel.ts`, `sliceView.ts`)

- **Colormap:** diverging, centred on 0: blue below 0, white at 0, red above, linear in `v / s` clamped to [−1, 1]. The scale s is `max(|p1|, |p99|)` of the shown finite values (auto), or a number the user fixes in a field next to an "Auto" checkbox (accepted when finite and in (0, 1e100]). When the auto scale is 0 (a constant 0 field, such as a tap muted to 0), every sample is drawn white and the histogram area says "constant 0". A non-finite value (never expected, §1.9) is drawn grey and counted.
- **Contour:** the 0 level (the density's surface: a voxel is solid when v > 0) drawn as line segments between samples where the sign of `v > 0` changes (marching squares on the sample grid), in an SVG overlay. The sea-level line (y 63) and the y control's level on vertical planes.
- **Histogram** beside the image: 64 bins over [p1, p99] (values outside fall in the end bins), and p1, p50, p99, sd and % < 0 printed; when p1 = p99 a single bar and "constant v". Percentiles are nearest-rank (`sorted[⌈q·N⌉ − 1]`), sd the population standard deviation, % < 0 the share of values below 0, all over the finite values.
- `blocks` uses the Voxels palette and legend (`VOXEL_COLORS`, `section.ts:149-167`) in the histogram's place; `rule` two colours, grey for n/a, and the share of 1s among the solid voxels in the histogram's place.
- The canvas holds n × n pixels scaled by CSS with `image-rendering: pixelated` (as the Voxels image, `section.ts:134-139`) into a square box whose side is the smaller of its cell's width and height (at least 128 px, §3.1), so the hover maps a pixel to a sample by `⌊(px / side) · n⌋`. A vertical slice is therefore not to scale (L blocks by 384); its axes are labelled in blocks. A slice of an older session epoch is dimmed with a "stale" label (`sectionView`, `src/ui/crossSection/model.ts:201-218`).

### 4.4 Point samples for horizontal planes (D16)

At voxel (x, y, z) the reference reads ColumnSample fields only at the four quart corners of the voxel's cell: `interpolated` reads `s.f[field][latticeIndex(i, j)]` for i ∈ {ci, ci+1}, j ∈ {cj, cj+1}, ci = lx >> 2 (`src/gen/density/reference.ts:81`), and an outside `col` reads the same four corners bilinearly (`readField`, `src/gen/column/columnStage.ts:116-132`, whose clamp to 3 gives the same cell for lx 12 … 15). A horizontal sample therefore needs only those four lattice points, not a whole ColumnSample (49 points, 49 steep stencils, rivers, lakes and the biome pick, `columnStage.ts:64-106`). `buildCornerSample(ctx, x, z, withSteep)` fills them with `columnPoint` (`samplePoint`, `src/gen/column/columnPoint.ts:60-77`), whose values equal the lattice's bit for bit (`columnStage.ts:1-5`, DT2's batch == point), and leaves the other lattice entries NaN; `withSteep` is true only when the evaluated expression reads `col steep`, **following refs** into the defs it reaches. Within one part, corner points are memoised by lattice coordinate (a `Map`; at extent 256 a 128² slice has 65,536 corner reads of about 4,225 distinct points), which leaves every value bit-identical. Measured (`map-workers.md` §7), a 128² horizontal slice at extent 8192 costs 7.0-7.2 s of whole ColumnSamples on one thread but 0.43 s with four-corner samples (1.44 s with steep). A test asserts, at 4,096 random voxels and for every `SAMPLE_FIELDS` field and both `withSteep` values, that the reference value from a corner sample is `Object.is`-equal to the one from the full ColumnSample; a field for which it is not is read from the full ColumnSample instead (a rule in `gen/inspect/fieldSlice.ts`, pinned by the same test). Corner samples never enter the DensityContext's ColumnCache (`src/gen/density/columnCache.ts:282-306`). Vertical planes use the ColumnCache's full samples (one per chunk column along the line).

### 4.5 Requests, draft and cancellation

- **What triggers a slice.** Every session edit (trees, sliders, mutes, seed, profile), a change of field, plane, line, centre, y, extent or (for the `selected` field only) selected node, and showing the tab. A slice for session epoch e can run only once the pool is configured with e's draft, so `DriverStatus` gains `sessionEpoch` (the session epoch of the draft the pool's last resolved configure holds; today `Cycle.sessionEpoch` is private, `src/ui/map/previewDriver.ts:55-65`), added to `emitStatus`'s change test (`previewDriver.ts:87-92`). The view requests whenever that pair (`poolEpoch`, `sessionEpoch`) changes, for the session epoch the configure holds, not on `settled` as the cross-section does (`crossSection/model.ts:151-153`); a result whose session epoch is older than the session's is shown dimmed as stale (§4.3). During a gesture a draft that arrives while a preview cycle runs waits in the driver's latest-wins slot (`previewDriver.ts:192-197`), so drafts are drawn whenever a configure lands, and the full slice follows the gesture's end. A reply is attributed by the pool epoch it carries.
- **Draft then full.** Each request runs a 32² draft first, then the 128² slice. The draft's priority is 2 (preview tiles take their distance in tiles, `src/ui/map/viewMath.ts:31-38`, so the draft follows the tiles at distance 0 and 1) and its total work is at most `DRAFT_BUDGET` (§5.2), so a draft never holds every worker ahead of the map. The full slice's priority is 500 (as stats and slices, `src/engine/workerPool.ts:292`, `315`); after an edit above `terrain` it waits behind the preview tiles, so the 300 ms target (§9) is the slice job's own time, not the end-to-end latency after such an edit.
- **Cancellation.** Every new request supersedes the previous one: its queued parts are dropped (`JobCancelled`) through the handle `pool.fieldSlice` returns (`cancel()`; today only `cancelTiles` exists, `workerPool.ts:357-362`), and the results of parts already running are discarded by a request token. Running parts are not interrupted at the same epoch (Open point 1): the work bound (§5.2) keeps each part short, and a second abort cell would break the 4-byte abort protocol (`src/workers/protocol.ts:114`, `protocol.test.ts:56`). A configure (new epoch) still aborts running parts through the existing cell, which the evaluation polls **once per sample** (one `Atomics.load`), so an in-flight part stops within one sample's time (at most `PART_BUDGET / n` units).
- The request stream is a pure model (`createFieldSliceRequests` in `sliceModel.ts`) with the cross-section streams' rules (`createLineRequests`, `crossSection/model.ts:115-172`): one result per (session epoch, request key), a token per request, `JobCancelled` keeps the last image silently, other errors show `failed`. The request key holds the node path only for the `selected` field, and only the plane's own geometry (the line on a vertical plane; the centre, extent and y on a horizontal one: the vertical evaluation does not read y, whose level line is only drawn). The stream requests only while no newer configure has been issued since the resolved one (the pool's epoch equals the status's `poolEpoch`), and costs the request on that configure's draft params (the page keeps each draft's params by session epoch), so the worker's own bound check agrees.

## 5. Worker jobs and probe changes

### 5.1 `fieldSlice` (`protocol.ts`, `fieldSliceJob.ts`, `taskHandler.ts`, `workerPool.ts`, `gen/inspect/fieldSlice.ts`)

- `FieldSliceMsg {type: 'fieldSlice', jobId, epoch, plane: 'vertical' | 'horizontal', ax, az, bx, bz | cx, cz, y, extent, n, field: 'density' | 'node' | 'blocks' | 'rule', path, from, to}`. `path` is the node path inside its leaf ('' for `density` and `blocks`). `[from, to)` is a range of sample columns: point indices along A → B (vertical) or rows j (horizontal). (`y` is required on both planes; it is unused by the vertical evaluation.)
- `FieldSliceResultMsg {type: 'fieldSliceResult', jobId, epoch, n, field, from, to, values: ArrayBuffer, fluid: ArrayBuffer | null}`: Float64 values for `density` and `node` (8·n·(to − from) bytes), u16 states plus u8 fluid for `blocks` (2·n·(to − from) and n·(to − from)), u8 for `rule` (n·(to − from)), each sample column's n samples in row order.
- **Guards.** `parseToWorker` checks the shape (types, the plane's keys present and the other plane's absent, `path` a string ≤ 512 characters). The handler answers `BAD_ARGS` for: n ∉ `SLICE_NS`; the segment (`segmentProblem`) or the square (§4.2) invalid, or non-integer coordinates; y not an integer in −64 … 319; extent not in `SLICE_EXTENTS`; `blocks` or `rule` on a horizontal plane; a `path` that does not name a node of the right kind in the configured **source** tree (`node`: a density node of `params.density.defs`, looked up own-property only, §1.7; `rule`: a rule or condition id); `0 ≤ from < to ≤ n` false; the work bound exceeded (§5.2, message `too heavy: …`). `parseFromWorker` checks the reply: n ∈ `SLICE_NS`, field in the set, `0 ≤ from < to ≤ n`, and the exact byte lengths for that n and field (as `sliceResult` checks its constant `SLICE_ROWS`, `protocol.ts:212-221`); the pool then checks that n, field, from and to match the request, as `stats` checks `args.len` (`workerPool.ts:309`).
- **A reply that fails its guard.** Today the pool drops it (`if (msg === null) return;`, `workerPool.ts:206-207`) before freeing the worker, so the job never settles and `pump` never gives that worker another job (`workerPool.ts:173`). `parseFromWorker` gains a third outcome: when the envelope (`type`, `jobId`) is readable but the body fails its guard, it returns `{bad: true, jobId, reason}`; the pool rejects the busy job with that `jobId` with `Error('BAD_MESSAGE: <reason>')` and frees the worker. This applies to every job reply type (the wedge exists for all of them), not only the new ones. A `workerPool.test.ts` case pins it.
- **Evaluation** (`src/gen/inspect/fieldSlice.ts`, under gen's determinism rules, `test/arch/rules/banned.ts`; the worker's `fieldSliceJob.ts` only parses, calls and replies). Per sample column: get the samples (vertical: the ColumnCache's ColumnSample of each chunk column; horizontal: corner samples, §4.4), then per sample poll `stop()` (ABORTED on a new epoch) and evaluate. `density` uses the GenContext's memoised DensityReference of the resolved tree; `node` a DensityReference of the evaluated expression of §3.4, memoised per (GenContext, path) in a small LRU (8 paths) inside a `WeakMap` keyed by the context; `blocks` uses the slice job's store and LRU (`src/workers/sliceJob.ts:40-43`, `114-120`) with the §4.2 points, through an injected T-column source (gen cannot import `workers/`), which the worker builds on a new `SliceJob.column()` (so `slice` and `fieldSlice` share one store and a configure empties both); `rule` rebuilds the column's scan through `surfaceProbeColumn`'s one-column cache (`src/gen/surface/probe.ts:35-48`; consecutive points along the line share columns), with the part's `stop()` threaded into that build's density fill (polled every 8 corner rows, as the T stage polls it; a stopped build leaves the cache empty), so a `rule` part on a heavy valid tree, whose probe column takes about 0.1 s near the column-cost maximum, still stops within §4.5's 50 ms.
- **The pool.** `pool.fieldSlice(req, {priority, columnCost, budget}) → {promise, cancel}` splits [0, n) into contiguous parts (§5.2), enqueues them as one group (a failing part drops the others, `workerPool.ts:236-242`), merges them by index into one n × n buffer, and checks each part's reply against its request. `instrumentPool` forwards the new methods (`src/ui/map/perfHook.ts:203-231`). The handler gets an explicit branch per message type and an exhaustive `switch` (the last line today answers `pointResult` for anything that reaches it, `src/workers/taskHandler.ts:191`).

### 5.2 The work bound (deterministic)

- **The evaluated expression.** `density`: the resolved tree's root; `node`: §3.4's expression, wrapped in `interpolated` when it has an interpolated ancestor (so it costs 1 + 8 × the subtree, which is what is evaluated). `gen/inspect/cost.ts` computes its **work cost**: 1 per node; `noise` and `noise2` `4 × octaves × (double ? 2 : 1)` of the configured noise leaf (a default `jag` or `overhang` noise costs 16, `detail` 8); `ref` its def's; `interpolated` 1 + 8 × its child; saturating at 2^31. The weights and factors are module-private. The default root's work cost is 569 (322 structural units, of which 17 noise evaluations: 8 `jag` and 8 `overhang` corners and 1 `detail`); a unit test pins it.
- **The unit.** One work unit is about 14 ns of reference evaluation on one thread: the default root takes 7.8 µs for 569 units (13.7 ns; `map-workers.md` §7), and the measured noise-heavy worst case, an `add` of 4,096 16-octave double `noise detail` leaves, 3,879 µs for 528,383 units (7.3 ns; `spec-review-security.md`). The first draft's unweighted model was off by up to 16 × on such trees.
- **Column cost.** The pool splits by sample columns, whose cost is `n × (c + perSample) + perColumn`, with c the work cost per sample and the acquisition costs (constants in `core/constants.ts`, since gen's `sliceCostOf` reads them and cannot import `workers/`; re-exported by `protocol.ts`; measured in `map-workers.md` §7):
  - vertical `density`/`node`: perColumn `COLUMN_SAMPLE_COST` = 2^15 (one ColumnSample, about 430 µs, charged once per sample column; neighbours sharing a chunk column are not credited);
  - horizontal `density`/`node`: perSample `CORNER_SAMPLE_COST` = 2^11 (about 26 µs), or `CORNER_STEEP_COST` = 5 × 2^10 = 5,120 (about 64.5 µs, the calibration's measure) when `withSteep` (2^13 would make n² × 2^13 = `REQUEST_BUDGET` at n = 128: every steep-reading tree's 128² horizontal slice refused, "limit 0");
  - `blocks`: perColumn the T column's work cost (`tColumnCost`: the density column cost of §1.7 with the configured noise weights plus the rules column cost, value-independent as tier 2 judges it; no `COLUMN_SAMPLE_COST` on top), 5,006,893 at the defaults; `rule`: the same plus n × the rule tree's node count (163).
  The UI computes the column cost with `sliceCostOf(params, field, path, plane, n)` and passes it; the worker recomputes it with the same function from its configured params and refuses a part above the bound, so the client is not trusted and both use one tree. `sliceCostOf` and the evaluated expression live in `gen/inspect/fieldSlice.ts`, not `cost.ts`: they need `resolveDensity`/`resolveDensityNode` from `gen/density/source.ts`, which imports `cost.ts` for tier 2, so placing them in `cost.ts` would make an import cycle; `cost.ts` keeps the cost primitives (`structuralCost`, `workCost`, `densityColumnCost(source, params?)`, `rulesColumnCost`, `ruleNodeCount`, `tColumnCost`), one function each. The split and refusal math is one pure function, `planFieldSlice(n, columnCost, poolSize, budget)` in `workers/protocol.ts`, used by the pool and the UI's notices; the worker's bound check (`fieldSlicePartProblem`, same file) uses the same k, so planned parts always pass.
- **Budgets** (`core/constants.ts`, re-exported by `protocol.ts`): `PART_BUDGET` = 2^23 units per part (about 115 ms at the default's rate), `DRAFT_BUDGET` = 2^24 per 32² draft (about 0.23 s of CPU over all workers), `REQUEST_BUDGET` = 2^27 per 128² slice (about 1.8 s of CPU).
- **Split:** a part holds `k = max(1, ⌊PART_BUDGET / columnCost⌋)` sample columns; the number of parts is `max(poolSize, ⌈n / k⌉)` (at most n) with equal contiguous ranges, never larger than k. A `density` or `node` request is refused before any job when one sample column exceeds `PART_BUDGET` or `n × columnCost` exceeds its budget; the view then keeps the draft with the notice "node too heavy for a 128² slice (cost c, limit L)", or, for a refused draft, "node too heavy to slice (cost c, limit L)". At the defaults: vertical 128² costs 128 × (128 × 569 + 2^15) ≈ 13.5 M units (10 % of the budget, k = 79), horizontal 128² 128 × 128 × (569 + 2^11) ≈ 42.9 M (k = 25); a 128² slice is refused above c ≈ 7,936 vertical or 6,144 horizontal (about 14 × and 11 × the default), a draft above c ≈ 15,360 or 14,336 (about 27 × and 25 ×); a horizontal slice of a tree that reads `col steep` above c ≈ 3,072 (128², 5.4 ×) or 11,264 (draft, 20 ×). Every acquisition cost leaves a per-sample room of at least the default's work cost under every budget (a unit test), so the notice never says "limit 0". `blocks` and `rule` are never refused here: tier 2's column-cost bound (§1.7) caps one column, k may be 1, and such a part may exceed `PART_BUDGET`, up to one T column at 64 × today's cost.
- So a density part never holds a worker longer than about `PART_BUDGET` units, a draft never takes more than `DRAFT_BUDGET` before the map's nearest tiles (§4.5), and the full slice queues behind every preview tile (priority 500).
- **Calibration.** The plan's real-thread worker task (after the protocol task, on a quiet machine with no other task's tests running) measures the unit on the default tree and on `slice.partWorst`'s noise tree (§9), in an integration test gated by `SLICE_CALIBRATION=1` that asserts the stop conditions below; if a part at `PART_BUDGET` takes more than 250 ms p50 on one thread, or the acquisition costs differ from the constants by more than 2 ×, the constants are re-pinned in this spec before the bench rows are recorded (§9's `slice.partWorst` then gates them).
- Determinism: the split depends only on (n, columnCost, pool size), the costs only on the configured params and the request, and the merged buffer is independent of the split (a test, §10). A time budget would only be expressible in the worker layer and would cut work nondeterministically (`map-workers.md` §8); it is not used.

### 5.3 `fieldProbe` and the other probe changes (D17)

- `FieldProbeMsg {type: 'fieldProbe', jobId, epoch, field: 'density' | 'node' | 'rule', path, x, y, z}` → `FieldProbeResultMsg {type: 'fieldProbeResult', jobId, epoch, value: number}` (for `rule`, 0, 1 or 255 for n/a). BAD_ARGS for non-integer coordinates, a position outside the window, y outside −64 … 319, a bad path, or, for `density` and `node` only, a work cost per sample (with its acquisition cost, §5.2) above `PART_BUDGET`. A `rule` probe is never refused by the bound, as `rule` slices are not: its acquisition is a T column (5.0 M units at the defaults, up to 64 × the default's under tier 2), bounded by tier 2's column cost. (A valid tree's evaluated work cost is at most about 6.23 M units under tier 2's column-cost bound, so the density/node refusal is a guard.) The reply guard accepts any number (NaN and ±∞ included; the readout shows them, §3.6). It polls `stop()` before building a ColumnSample or a T column and before evaluating, so a new epoch interrupts it between those steps; a `rule` probe's column build also polls it in its density fill (§5.1). `pool.fieldProbe(req, priority = −1)` is a single job. It evaluates exactly the function `fieldSlice` evaluates for one sample, so hover and slice agree.
- The worker memoises one `DensityReference` per GenContext (`densityReferenceOf(ctx)`, a WeakMap, built on `surfaceContextOf(ctx).density.expr`, the stage's own resolved tree) for `density`, and the per-path ones of §5.1 for `node`; nothing memoises one today (`map-workers.md` §6).
- Configure validates the trees (§1.8). The `surfaceProbe` handler polls `stop()` before its column build (`taskHandler.ts:185-189`); its column is bounded by tier 2's column cost (§1.7). `surfaceProbe` itself, the compiled `probe` (`src/gen/density/probe.ts`, used by `surfaceEst3`) and the other existing jobs are unchanged.

## 8. Goldens and `GENERATOR_VERSION` (D14)
