## Goal

The world has no edge. After SP4a's first entry (the start screen, the loading screen that waits for the whole render distance, the reveal at once), the coordinator keeps loading the world around the camera while the user flies, and unloads what is left behind, with no stutter: new terrain appears column by column behind the fog, each column at once, never section by section; when the user flies faster than the machine can generate (96 blocks/s, 384 with Ctrl), empty areas may show for a while, but the camera is never slowed and the frame never freezes. WASD fly horizontally (Minecraft's creative flight), Space and Shift change the height. The render distance changes live from the help's settings: raising it streams new terrain in behind the fog, lowering it drops the far terrain. Before any of that, SP4b shards CI's unit tests into two parallel jobs. Underneath: the store's concurrency fixes that unloading makes reachable, the per-scope epoch cells, and both section renderers' streaming halves (RegionBatch in Chrome, RegionMesh in Firefox). It is measured by a `?bench=medium` streaming route (G1 while streaming) and a deterministic R7 metric. The user's own check is flying around, and a long way in one direction, without stutter on the Iris Xe and on the RTX 3060 Mobile. The generated world does not change (`GENERATOR_VERSION` 5, the 59 goldens byte-identical).

## Decisions taken by this spec (for the user's review)

The brief and the maps left these open. The recommendation is the text of the section cited; the alternative is stated.
- **D1 The unit project is sharded by named heavy files plus a catch-all** (§1.1): `.github/scripts/unitShards.mjs` holds `heavy` (the ten slowest unit files, 202 s of the 412 s summed in CI run 39950653330) and `rest` (every other file, 210 s), on a shard library shared with `metricShards.mjs`, whose `check` fails a job unless the shards cover the project's files exactly once. Alternative: `vitest --shard=1/2` and `2/2` (no list to keep, but it splits by file count: 245 s / 168 s summed on today's data, and a new heavy file lands wherever its path hashes).
- **D2 `check` keeps build, arch and integration; the unit shards run on both paths** (§1.2): arch needs the full history and `GOVERNANCE_BASE`, integration needs idle CPUs and runs one file at a time; the two unit shards run on the docs-only path too, because `uiSmoke.test.ts` and `reviewSlices.test.ts` read files under `docs/`. Alternative: integration inside one unit shard (that shard then becomes the longest job).
- **D3 The coordinator's reader pins protect every write it orders** (§2.10, §3.5): per column, the number of in-flight jobs reading its proto (D) and its final set (L, MESH); a column is freed, or its proto dropped, only at zero, so no job ever sees a neighbour vanish. This covers unload, proto retention, retries and SP4c's Apply. Alternative: rely on the store protocol alone (D4), with jobs that meet a vanished neighbour failing and being retried.
- **D4 Deferred reclamation is built now, and every slot release goes through it** (§2.5): reader epochs per thread in a shared buffer, a limbo list per thread, a released slot freed only once every reader that could hold it has finished; a release with no reader inside a read section (or on an unshared store) frees at once, so single-threaded stores and today's tests keep immediate reuse. In SP4b the pins (D3) already make every write safe, so the protocol is defence in depth, exercised by every real free while streaming; SP5's sim worker, whose writes the coordinator does not order, is its first necessary consumer. It is the cut line's first item (§10). Alternatives: write the protocol here and let SP5 build it; a seqlock (detects a torn read after the fact, so a reader must survive garbage state ids).
- **D5 Versions stay monotone across a record's life, and the claim generation goes in int 12** (§2.2, §2.3): `clearRecord` no longer resets `blockVersion`/`lightVersion`, so a stale result never matches after a free and re-claim; `find` and the writer's `check()` validate the generation. Alternative: reset versions on claim and add the generation to every result's recorded versions.
- **D6 The pool lock word holds its owner, and a dead owner is a fatal store error** (§2.6): the lock stores `thread + 1`; the pool marks a failed worker's thread dead (its reader epoch cleared, so reclamation goes on), and a thread spinning on a dead owner's lock throws `StoreCorrupt`, which reaches the page (on a worker, as the reply code `STORE_CORRUPT`) and shows the failure panel instead of freezing every thread. Alternative: a spin timeout without an owner (a slow holder and a dead one look alike).
- **D7 The per-scope epoch cells replace the pool-wide abort cell on every pool** (§2.7): each job carries two values, `epoch` (the configure generation, as today, for `STALE_EPOCH` and the pool's settle check) and `scope` (its phase's cell at issue, for the stop); `configure` stores the new generation into all four cells; `bumpScope(from)` is the one small API built for SP4c's Apply, unit-tested and called by nothing else in SP4b (the slot table's per-column epoch and MESH's epoch rule are SP4c's, §12.1). Alternative: keep the pool-wide cell until SP4c (SP4a D5's plan, made obsolete by the split).
- **D8 Cancellation drops queued work and lets in-flight jobs finish** (§3.6): jobs that leave the needed set leave the coordinator's heaps (the pool's queue holds at most N world jobs, and `cancelWorld(pred)` drops those); a job already running (T ≈ 2-3 ms, L ≈ 2-3 ms, a column's mesh ≈ 2-5 ms at SP4a's bench) finishes, and intake keeps or discards its result. Alternative: a per-job abort cell (a third abort mechanism for at most N short jobs).
- **D9 The coordinator's state lives in a per-torus-slot table, and the needed sets come from per-RD membership tables** (§3.1, §3.2): 4096 preallocated entries mirror the store's records; on a crossing every slot is classified in one pass from a table over the offsets within RD + 5. Zero allocations, any move length (SP4c's teleport is a long crossing). Alternative: SP4a's offset-indexed arrays rebuilt per crossing (allocations, and the indexing cannot follow the centre).
- **D10 Four heaps keyed by master §4.3's score with the view term, rebuilt on a crossing or a turn > 30°** (§3.3): `d_h` from the camera's column, `θ` from the yaw at the rebuild, so a score does not change between rebuilds. Alternative: scores from the camera's exact position re-evaluated every frame (a rebuild per frame).
- **D11 Proto retention is built, and the page keeps every proto while D places nothing** (§3.7): the rule (a proto freed only at status ≥ Decorated), `freeProto`, the alive bit and `T(protoOnly)` are built and tested with retention on; the page runs `retainAllProtos: true`, because with SP4a D7's shared slots a freed proto saves no memory and a regenerated proto stops sharing with its final set (doubling those sections). The first D feature (SP8b) turns it off. Alternative: run the rule live from SP4b.
- **D12 After the reveal, errors degrade instead of stopping the world** (§3.6): cancelled and dropped results requeue; an `INTERNAL` job retries once, then the column is skipped with a notice until its voxels unload (a column that comes back into range is retried from scratch, so no hole is permanent); `StoreFull`, which the store's reservation cap makes an error expected never to happen, pauses new T jobs, is counted in the HUD and the bench JSON, and raises a notice offering "Lower to RD n", never applied automatically (SP4a's rule for the RD suggestion); a failed worker lowers N; only zero live workers, a dead lock owner or a worker's `STORE_CORRUPT` shows the failure panel. The first entry keeps SP4a's rule (any error stops the load). Alternative: every error fatal, as SP4a.
- **D13 The upload budget is 2 ms and 32 section rows per frame, with at most one structural operation per frame** (§3.9): a structural operation is creating a region's batch or arena, growing it (vertices, indices or instances), optimising or compacting it (each a full buffer upload of about 2 MB); the ready queue is ordered by the MESH score from the camera (one function in `core/streamScore.ts`, shared with the coordinator's heaps); a region with pending update ranges is drawn without frustum culling in the frame its rows were written, so three uploads them in that frame, under the cap, and never in a later burst when the user turns toward them; while the loading screen is up, structural operations are uncapped (bounded by its 12 ms). Alternative: the time budget alone (GL uploads happen inside `render()`, which a CPU clock does not see).
- **D14 RegionBatch: region-local instance matrices, reservations, growth ×1.5, `optimize()` instead of growth above 40 % fragmentation** (§4.2): each region's `BatchedMesh` carries the region's origin in its own transform, so a floating-origin rebase moves about 20 objects instead of every instance, and instance ids may be reused (the dense-id hand-over disappears). Reservations: opaque 131,072 vertices / 196,608 indices, translucent 16,384 / 24,576, cutout created on demand at 8,192 / 12,288, 1,536 instances (grown × 1.5 by `setInstanceCount` when full, a structural operation). Removed rows are hidden at once and their geometry released in `pump` under the frame's budget. The spike's churn timings bound only the CPU half of a structural operation; the bench records each one's frame (§8.3). Alternative: SP4a's per-instance origin matrices (a rebase re-places about 20k instances in one frame, every 10.7 s at 96 blocks/s).
- **D15 RegionMesh: an arena per region and pass with column ranges, hidden by degenerate indices until the reveal frame** (§4.3): a first-fit free list of vertex and index ranges, `addUpdateRange` of the written ranges only (with `needsUpdate`), compaction in place above 40 % free space, or growth ×1.5 otherwise into a new geometry with the old one disposed in the same frame (three cannot resize an attribute). Alternative: re-merge the region on every change (SP4a measured about 2 ms per region on the Iris Xe in Firefox: the whole frame's budget for one column).
- **D16 The swap seam is SP4c's** (§4.4): no SP4b path stages a revealed column again (MESH is issued only for an unmeshed column, and a dropped MESH result is never staged), so in SP4b `stage` on a revealed column throws, a coordinator test asserts that no revealed column is re-staged, and SP4c builds the swap (the old rows visible until the new ones are uploaded, then swapped in one frame) together with Apply, `bumpScope`'s first caller and the per-column epoch. Alternative: build it now (dead paths in both renderers' staging, which the contract suite would cover with no SP4b caller).
- **D17 The fog ends at (RD − 1)·16 blocks, and the edge fade goes** (§6.3): without the fade, the nearest corner of a column just outside the mesh disc can be 177 blocks from the camera at RD12 (the camera off-centre in its column, the column on a diagonal), inside SP4a's fog end of 184; at 176 it is always fully fogged. The band stays 64 blocks (RD12: 112-176). **A visible change** to the first view and to every RD (8 blocks less, RD4 −14 % to RD16 −3 %), so it is **the user's choice**, with the numbers per RD (Points for the user's review, 1). Alternative: keep (RD − 0.5)·16, where such a gap shows sky at about 97 % fog (nearly the fog's own colour).
- **D18 Live render distance** (§5): any integer in [4, min(16, the reservation's cap)]; raising it moves the fog outward as the rings fill, never faster than 32 blocks/s; lowering it brings the fog in at once and removes the far terrain over the following frames (≤ 64 columns hidden for removal, their rows released under the upload budget, and ≤ 16 column frees per frame); the camera's far plane follows; the slow-frame notice lowers the RD live on a click. Alternative: the fog jumps to the new distance at once (empty far rings visible through thin fog after a raise).
- **D19 Flight keeps SP4a's vertical range** (§6.1): y from −64 to 400, the speeds and keys unchanged; as in Minecraft's creative flight, the horizontal and vertical speeds are independent (rising while flying forward keeps the full forward speed). Alternative: a higher ceiling for the contemplative view.
- **D20 R is unbound** (§6.2): `loadHere` leaves the key map; no replacement action, so SP5 can take the key. Alternative: R as "re-centre the world here" (streaming does it already).
- **D21 The first entry runs on the streaming coordinator** (§3.11, §7.1): the same per-frame `update` at the spawn, with reveals held until the whole mesh set is uploaded (the loading screen's 12 ms budget), then SP4a's single reveal. Alternative: keep SP4a's `load()` beside a separate streaming path (two schedulers to keep consistent).
- **D22 The bench route is `?bench=medium`, run through the page's own loop** (§8.3): seed 42, RD12, a 95 s script of legs at 20, 96 and 384 blocks/s with turns, a hover and a live RD change, the time running at ×60; `?flight=sp4a` stays as SP4a's static route. Alternative: extend `?flight` (it replaces the page's loop, so nothing would stream).
- **D23 G1's streaming cells, defined** (§8.4): over the bench's scripted frames, p95 ≤ 16.7 ms, no frame > 33 ms (snapped, as SP4a's flight counts them), ≤ 100 draw calls and main thread ≤ 6 ms p95; the RD12 fill ≤ 6 s is the first entry's reveal time with `?workers=4`; the GPU estimate ≤ 150 MB is §8.4's one formula (the section renderer's allocated geometry, the texture array, the lightmap, the sky and the drawing buffer); the frames holding a structural operation obey the same no-frame-over-33-ms rule. On the RTX 3060 Mobile, the Chrome cell's no frame > 33 ms and p95 ≤ 16.7 ms at Medium are checked at the exit like D28's Firefox cells (the user's rule holds on both GPUs); only the High-preset parts (p95 at High, JS heap + SAB ≤ 450 MB) wait for SP11's High preset. Alternative: fill measured on a fresh area after a long flight (it depends on the route's speed, not the machine).
- **D24 R7 is a deterministic Node metric** (§8.1): the real coordinator, the real pool over in-process task handlers on a shared store, both real section renderers (three without a context), a fake clock and a scripted camera; each frame an independent probe reads three's objects for columns showing some but not all of their rows. The browser bench records the same probe. Alternative: R7 from the bench JSON only (one run per GPU cell, not in CI).
- **D25 Zero allocation covers the frame at rest, not only the coordinator** (§3.10): `coordinator.update`, the section renderer's `pump`, the materials' uniforms, the lightmap, frame timing and the page's frame step allocate nothing without movement or arriving results; tested with a heap-growth bound. "Nothing" counts the objects our code creates; V8 boxing a fresh double as a HeapNumber where it crosses a call TurboFan does not inline is the engine's calling convention, so the whole frame step has a boxing budget of 256 B per tick (about 10 boxed doubles, 158 B, measured on Node 24), its parts the 26 B per call bound (amended by Task 23, rulings R7). Alternative: the coordinator's `update()` only (the master's literal test; SP4a's dozen per-frame objects would stay).
- **D26 SP4c (M; SP4b) and SP5 (M; SP4b, SP4c)** (§11): SP5's sim worker writes Published columns under SP4b's deferred reclamation, and its fork dialog (b) fires on the first Apply (master §2.7), which is SP4c's, with E6 testing every option; so SP5 follows SP4c and the critical path runs SP4a → SP4b → SP4c → SP5. Alternative: SP5 on SP4b only, E6's Apply branch tested once SP4c lands (SP5 could run alongside SP4c).
- **D27 The two cheap mesh-job levers are applied** (§3.13): the mesh job fetches the nine `ColumnView`s once per column and passes them to `isTrivial`, `copyPaddedSection` and `fluidDepths`, and `meshFluid` skips sections `fluidDepths` found dry. Alternative: only if the bench shows MESH lagging.
- **D28 The Firefox cells and the RTX Chrome cell are checked at the exit, not gated by a row** (§8.4): the user's `?bench=medium` runs on RegionMesh must have p95 ≤ 25 ms, ≤ 100 draw calls and no frame > 33 ms while streaming; the RTX Chrome run at Medium p95 ≤ 16.7 ms and no frame > 33 ms; every committed bench file `partialColumnFrames` and `mixedColumnFrames` 0; a miss after tuning comes back to the user. Alternative: record them only.
- **D29 The throttle caps generation** (§3.8): `genCap` limits the T, D and L jobs in flight, from max(1, N − 1) down to 1 (the throttle's maximum follows `liveWorkers()`, so one surviving worker still generates); MESH keeps its own cap N and the total stays ≤ N; "slow" is a p95 above max(16.7 ms, the display interval + 0.5 ms) and "fast" a frame under max(13 ms, the display interval + 0.5 ms) (the user's decision of 2026-10-24: the thresholds follow the display). Alternative: throttle T only.

### 2.2 The claim generation (`columnTable.ts`, int 12)

- `REC_GEN` = 12, even while the record is free, odd while held. `claim`: CAS `claimed` 0 → 1, `clearRecord`, store cx, cz and epoch, then `Atomics.add(gen, 1)` (odd). `unclaim`: `Atomics.add(gen, 1)` (even), then cx = cz = `NO_COLUMN`, then `claimed` 0.
- `find(cx, cz)`: `g1 = load(gen)`; −1 when `g1` is even; check `claimed`, cx, cz; `g2 = load(gen)`; the base only when `g1 === g2`.
- The writer captures the generation at its claim or reopen, and `check()` throws `WriterStale` when it changed.
- Master §2.3's record table gains the row "12 | claim generation (even free, odd held; SP4b)".

### 2.3 Monotone versions (D5)

### 2.5 Deferred reclamation (`world/store/reclaim.ts`, D4)

- **The buffer** (in `StoreHandles` as `reclaim`, 192 bytes, a `SharedArrayBuffer` when shared): Int32 [0] the global epoch G (starts at 1), [1] the dead-owner mask (§2.6), [2] the store id (a non-zero Int32 stamped at creation, §2.8: a per-thread counter starting at 1, since `world/` uses no `Math.random`; a store is created on one thread and attached only to that thread's workers; amended while planning), [16 + t] the reader epoch of thread t, 0 when idle, [32 + t] the number of slots in thread t's limbo, for t in 0…15: the main thread 0, the pool's workers 1…N in attach order (the `attach` message gains `thread`), the harness's threads 1…4, SP5's sim worker 15.
- **Readers:** `store.enterRead()` announces `e = load(G)`, `store(R[t], e)`, and repeats while `load(G) !== e`; `store.exitRead()` stores 0, then drains (below). The task handler wraps every world job in a read section; the main thread wraps its per-frame store reads (§2.4's accessors) in one.
- **Releases:** every `pool.free` that `section.ts` (`storeChannel`, `releaseEntry`, `shareEntry`) and `freeColumn` would make becomes `retire(pool, slot)`: `tag = Atomics.add(G, 1)` (the old G); then, when the store is unshared or every `R[t]` reads 0, the slot is freed at once (the fast path); otherwise (pool, slot, tag) goes on the calling thread's limbo list (a thread-local `Int32Array` ring of 3 × 1024 entries, grown only on overflow, in the cold path) and [32 + t] counts it. The fast path is safe: a reader that loaded G ≤ `tag` and has not yet published `R[t]` fails its re-check (`load(G) !== e`) and retries with a G that postdates the release, and every Atomics access is sequentially consistent. So a single-threaded store (`createStore({ shared: false })`), every test and harness that frees outside a read section (`test/unit/store.test.ts:165-166`, `:195-196`, `regionCache.test.ts:409`, `pool.test.ts`, `section.test.ts`, `storeReopen.test.ts`, `region.test.ts`, `test/integration/slabFuzz.test.ts` and `region.test.ts`, the metrics harness's in-process frees, `src/metrics/region.ts:37`, `:41`) keeps today's immediate reuse, and those tests' expectations stay valid unchanged.
- **Drain:** at every `exitRead()`, after a worker posts each reply, and once per frame on the main thread (after the coordinator's unloads): `m` = the smallest non-zero `R[t]` over the threads whose dead bit is clear (§2.6), or +∞; every limbo entry with `tag < m` is freed (`pool.free`, the refcount drop). A reader that announced `e` may hold a slot retired with tag ≥ `e`, never one retired before it announced, so no slot is reused under a reader. A worker whose limbo is still non-empty after a drain retries every 16 ms by a timer until it is empty, so an idle worker never keeps slots counted as used.
- **Cost and bounds:** one `Atomics.add` and 16 loads per release; a slot waits in limbo for the longest job that was running when it was released (milliseconds); the pools count limbo slots as used, so `StoreFull` accounting is conservative.
- **What it protects in SP4b:** nothing the pins (§2.10) leave open, by design: every SP4b free goes through it, so streaming exercises it under real load before SP5's sim worker (whose writes the coordinator does not order) relies on it (§12.2). The protocol is master §2.3's "post-commit reclamation protocol" (§13).

### 2.6 The lock owner (`pool.ts`, D6)

`attachPool(h, thread)` makes the lock word `thread + 1`: `lock()` CASes 0 → `thread + 1`; after the backoff saturates (`MAX_SPIN`) it re-reads the word every 4,096 spins, and when the owner's bit is set in the dead-owner mask it throws `StoreCorrupt('pool lock held by failed thread k')`.
- **A dead worker:** the pool's `fail(w)` (`workerPool.ts:277-295`) only terminates the worker and knows no store, so `createWorkerPool` gains an `onWorkerDead(thread)` option (the pool keeps the thread index each worker was attached with); the page passes `(t) => store.markDead(t)`. `markDead(t)` sets t's bit in the mask, then stores `R[t] = 0` (safe: the worker is terminated, so it reads nothing more), and the drain skips dead threads (§2.5), so a worker that died inside a read section does not hold every later release in limbo. Slots in the dead worker's own limbo stay counted as used for the session (at most its last job's releases).
- **`StoreCorrupt` from a worker:** today a worker's throw becomes `INTERNAL` (`taskHandler.ts:270-272`), which the coordinator would retry. `ErrorCode` (`protocol.ts:119`) gains `STORE_CORRUPT` (and its guard); the task handler maps a `StoreCorrupt` to it, the pool rejects with `StoreCorruptError`, and the coordinator raises the fatal event, so the world page shows the failure panel (§7.4), as for a `StoreCorrupt` on the main thread.
- The rule "never terminate an attached worker except after its `error`" stays.

### 2.7 The per-scope epoch cells (`epochs.ts`, `protocol.ts`, `workerPool.ts`, D7)

- `ConfigureMsg.abort` (`protocol.ts:42`, guard `isAbortCell` at `:200`, 4 bytes) becomes `epochs: SharedArrayBuffer | null` (16 bytes, guard `isEpochCells`): the store's `epochs` on the world page, a pool-owned 16-byte buffer on `?map` (created under isolation, as the abort cell is today, `createBrowserPool`, `workerPool.ts:578-582`).
- **Two values per job.** `epoch` keeps today's meaning, the configure generation: the worker answers `STALE_EPOCH` when it differs from its configure's (`taskHandler.ts:196`) and the pool settles a reply as `JobCancelled` when `job.epoch` differs from its own (`workerPool.ts:343`). Every job message (`WorldJobMsg`, and the tile, spawn, stats, slice, field and probe messages) gains `scope: number`, the value of its phase's cell at issue. Without the split, the first `bumpScope('light')` would make every later L and MESH job carry a cell value that differs from the worker's configure epoch, and each would fail as `STALE_EPOCH`.
- **Which cell a job reads:** terrain 0 (`terrain`, `spawn`, map tiles, stats, slices, field slices and probes), decorate 1, light 2, mesh 3 (`meshColumn`). The worker stops when `Atomics.load(cells, cellOf(type)) !== m.scope` (`taskHandler.ts:157-160`, now per cell) and replies `ABORTED`; the pool settles a reply as `JobCancelled` when `job.epoch !== epoch` or when its cell no longer equals `job.scope`.
- **`configure`** increments the pool's generation, stores it into all four cells (so the cells and the generation agree after every configure; the store's cells start at 0 and the pool's generation at −1, so the first configure makes both 0) and rejects every queued job (today's behaviour, `workerPool.ts:388-401`). **`bumpScope(from: 'terrain' | 'decorate' | 'light' | 'mesh')`** adds 1 to the cells from that phase onward and rejects the queued jobs of those phases: SP4c's Apply (master §5.1: "bumps the epoch from the dirty stage onward"). It is the one small API SP4b builds for SP4c; in SP4b nothing calls it outside its unit tests, which include "after `bumpScope('light')` a new L job succeeds".
- T claims its record with its job's epoch, as today (`REC_EPOCH`).

### 2.8 The pool's own fixes (SP4a hand-overs)

### 2.9 The race fuzz (`test/integration/columnTableFuzz.test.ts`)

Four `worker_threads` on one shared store, 100,000 operations, seeded (`SLAB_FUZZ_SEED`, validated: a non-integer seed is an error, SP3a §10):
- **column-table races**, with invariants that match the design (the writer's guard is check-then-act, `store.ts:207-211`, `:224-233`, and the pins, not the guard, keep a record from being freed under its writer): all four threads `claim` and `unclaim` the same 64 records concurrently (CAS contention: no two holders) and `find` against claims and unclaims (never a stale match, the generation consistent); versions never decrease. A record is freed only when no writer of it is live, ordered by a test-level ownership token per record (the fuzz's analogue of the pins); `WriterStale` is asserted only for writer calls that start after a takeover has completed, sequenced by an Atomics handshake;
- **cross-thread slot handoff:** a slot allocated and shared on one thread is freed on another; no double allocation and no refcount below 0;
- **deferred reclamation:** reader threads stamp a slot's content with a canary while inside a read section and check it at exit; writer threads retire and reuse slots; a reused slot under an active reader fails the test.
About 5 s, in the integration project (serial).

### 2.10 Who reads and writes what while streaming

The single-writer-by-status rule (master §4.1) with the coordinator's pins (§3.5):
- **T of K** claims K's record (free, or freed beforehand when it held a far column, §3.5) and writes K's proto and aux; nothing reads K until its commit at Proto.
- **D of K** reads the 3 × 3 protos (each pinned as a proto reader) and writes K's final entries at status 1; **L of K** reads the 3 × 3 final blocks, fluid and `LIGHT_BLOCKING` (pinned as final readers) and writes K's light at status 2; **MESH of K** reads the 3 × 3 Published sets (pinned).
- **The main thread** reads Published columns (the eye's light, `MOTION_BLOCKING`) and frees unloaded columns and protos; it frees K only at zero pins and when no job of K itself is in flight, so no reader ever sees a slot of K recycled. A worker frees only its own uncommitted column, on a stop or a throw (`fillColumnT`'s pattern, `src/metrics/region.ts:31-43`), and L's `resetLight` releases its own column's light; those releases go to the worker's limbo and drain after its reply (§2.5).
- **`T(protoOnly)` of K** writes only K's proto descriptors and the alive bit, at K's status ≥ 2 (Decorated or Published); readers of K's final set are unaffected (no final entry changes and nothing is freed: in SP4b every final slot is a shared proto slot whose final reference keeps it alive), and K's aux slots are not touched (§2.4).
- **Writes to a Published column in SP4b** are exactly two: `T(protoOnly)`'s proto descriptors and alive bit (never on the page while `retainAllProtos` is on, D11), and the main thread's frees under zero pins. Nothing writes a Published column's final set. SP4c's Apply and SP5's sim worker are the first writers of Published final sets (§12); master §4.1's single-writer rule is amended accordingly (§13).

## 3. The streaming coordinator (`engine/coordinator.ts`)

### 3.1 States and the per-slot table (D9)

- One entry per torus slot `s = (cx & 63) + 64·(cz & 63)` (4,096, preallocated typed arrays): the column it tracks (`cx`, `cz`, or none), its stage (Absent, Proto, Decorated, Published), `meshed` and its `meshSeq` (Uint32), `busy` (the stage of its in-flight job, or none), the pins `protoReaders` and `finalReaders` (Uint16), `protoAlive`, the set flags of §3.2, the retry count, `failed`, and each stage's heap position.
- The store's `status` stays the truth the workers read; the table mirrors it from results, as in SP4a.
- **Transitions:** Absent → Proto (T), → Decorated (D), → Published (L), → meshed (MESH, staged to the section renderer); a mesh unload clears `meshed` and bumps `meshSeq`; a voxel unload frees the record and returns the entry to Absent, clearing `failed` and the retry count (the record's versions keep growing, §2.3); `freeProto` clears `protoAlive`, `T(protoOnly)` sets it.

### 3.2 Needed and retained sets around a moving centre (`engine/rings.ts`)

- The needed sets are SP4a's (master §4.3): MESH the integer disc `dx² + dz² ≤ (RD + 0.5)²` around the camera's column, L, D and T each the previous set grown by the 3 × 3 (RD12: 489, 593, 705, 825).
- **Retained sets** (master §4.2's hysteresis): meshes are kept within the disc of radius RD + 1 (`≤ (RD + 1.5)²`) and voxels within RD + 5 (`≤ (RD + 5.5)²`, which contains the T set); the proto ring is the T set minus the L set (RD + 2 … RD + 3).
- **`membershipTable(rd)`**, cached per RD: one byte per offset in [−(RD + 5), RD + 5]² (43 × 43 at RD16) with the flags MESH, L, D, T, keepMesh, keepVoxels and protoRing. The torus check generalises SP4a's: 2·(RD + 5) + 1 ≤ 64 (43 at RD16; true up to RD 26), asserted for every RD the page accepts.
- **Classification:** on a crossing (or an RD change) every slot is evaluated once: the column the slot would hold inside the 64-wide window around the camera's column, per axis `c = camC + ((s − camC + 32) & 63) − 32` with `s` the slot's coordinate (`cx & 63`), so the offset `c − camC` lies in [−32, 31]; its flags come from the table (none outside RD + 5); a slot whose tracked column is a different one is due for unload first (§3.5). About 4,096 table lookups, ≤ 1 ms on a crossing (master §7's coordinator budget).

### 3.3 Priority: four heaps with the view term (D10)

- Master §4.3's score: `d_h − 3·max(0, cos θ)·[d_h > 2] − stageBonus` (MESH 1.5, L 1.0, D 0.5, T 0), `d_h` the column offset's length from the camera's column, `θ` the angle between the camera's horizontal forward (its yaw) and that offset; ties by colKey. It is one pure function in `core/streamScore.ts`, which the coordinator's heaps and the section renderer's ready queue (§3.9) both call (core is importable from engine and render; neither may import the other, `test/arch/rules/imports.ts:28-29`). `core/` follows the Math allowlist (no trigonometry, no `**`), so `streamScore(dx, dz, fx, fz, bonus)` takes the unit forward `(fx, fz)` the caller computed from the yaw (`[sin yaw, −cos yaw]`, `fly.ts`'s convention), `d_h` through `Math.sqrt`, and cos θ as the dot product over `d_h`, computed only when `d_h > 2` (amended while planning).
- One binary heap per stage, `Int32Array` slot indices over `Float64Array` keys, capacity 4,096 each; `pump` takes the smallest top among the stages whose cap allows another job (SP4a D6's rule), without popping held-back jobs.
- **Rebuild** (Floyd, O(n), n ≤ 4,096 per heap) on a crossing, on an RD change, and when the yaw has turned more than 30° from the yaw of the last rebuild. Between rebuilds a newly eligible job is pushed with its score from the last rebuild's centre and yaw.
- **Eligibility** (pushed when it becomes true, checked again when popped): T for an Absent column of the T set whose record is free; D for a Proto column of the D set whose 3 × 3 are ≥ Proto with live protos; L for a Decorated column of the L set whose 3 × 3 are ≥ Decorated; MESH for a Published, unmeshed column of the MESH set whose 3 × 3 are Published; and in every case not busy, not failed.

### 3.4 Re-centring

`update(cam)` compares the camera's column with the last one: on a change (one column or a thousand: SP4c's teleport is the same path) it re-classifies the slots (§3.2), schedules the unloads (§3.5), rebuilds the heaps (§3.3) and moves the upload queue's centre (§3.9). Without a crossing it only checks the turn, pumps the pool and runs the throttle. The floating origin is re-centred by the page from the camera, snapped to 512 blocks and rebased beyond 1024 (master §2.1); the first origin is `snap(the spawn)` (the SP4a hand-over, §7.6).

### 3.5 Pins, unload hysteresis and record collisions (D3)

- **Pins:** at `issue`, a D job adds 1 to `protoReaders` of its nine columns, an L or MESH job to `finalReaders`; `settle` (the worker's reply, a rejection or a failure: the pool settles a job only when its worker has stopped working on it) subtracts them.
- **Mesh unload:** a meshed column outside keepMesh is marked for removal in the section renderer (`sections.remove`: hidden at once, its rows released by `pump` under the frame's budget, §4.1) and its `meshSeq` bumped; at most 64 columns marked per frame.
- **Voxel unload:** a column outside keepVoxels, not busy and with both pins at 0, is freed (`store.freeColumn`); at most 16 per frame. The order is the score (§3.3) of the needed column that maps to the same torus slot (the T that the free unblocks), so after a long crossing the frees that unblock the nearest T jobs go first and terrain appears nearest-first (SP4c's teleport inherits this); a slot whose window column is not needed goes last. A column that leaves the T set but stays inside keepVoxels keeps its stage: its work stops, and it resumes where it was if it comes back. Its `failed` mark, if any, goes with the voxel unload (§3.1), so a column that comes back into range after leaving keepVoxels is retried from scratch.
- **Record collisions:** a T whose record still holds another column waits; that column lies at least 64 − (RD + 3) ≥ 45 columns from the camera on an axis, outside keepVoxels, so the unload frees it as soon as its pins drop, and the T becomes eligible. No `SlotBusy` reaches a worker. The coordinator counts the T jobs that waited on a collision (`collisionWaits`, in the counts).
- **Lowering the RD** (§5) uses the same rules from the next `update`.

### 3.6 Cancellation, intake and errors (D8, D12)

- **Cancellation:** a column whose eligibility ends (it left its stage's set) leaves the heap at the next pop or rebuild; `cancelWorld` drops its queued pool job; an in-flight job runs to completion.
- **Intake** (SP4a's version rule): T and D carry no versions; an L result is compared on the nine `blockVersion`s, a MESH result on all 18, against `versionsInto` into a preallocated scratch; a MESH result is also dropped unless its `meshSeq` equals the slot's and the column is still in keepMesh. A result for a column the slot no longer tracks is dropped (a T's committed record is then freed by the unload rule). A dropped result counts in `dropped` and requeues the column; none is expected in SP4b (nothing writes a Published column, and the pins forbid freeing a neighbour under a job).
- **Errors after the reveal** (D12): `JobCancelled` requeues silently; `INTERNAL` requeues once, and a second failure marks the column `failed` (skipped by every stage; its neighbours' dependent jobs wait, so a small hole shows) until its voxels unload, after which it is retried from scratch if it comes back into range (§3.5); the first such failure raises a dismissible notice "Some terrain could not be generated" with "Copy details", and more than 32 failed columns in a session shows the failure panel (a systematic fault, not a transient one); `StoreFull` (expected never to happen: the store's reservation caps the RD, `engine/renderDistance.ts:22-27`, so it points to a leak) pauses new T jobs until the next voxel unload frees slots, counts in the HUD's and the bench JSON's `storeFull` errors, and raises a dismissible notice offering "Lower to RD n" (the next lower RD, `lowerRd` in `engine/renderDistance.ts`, amended while planning; applied live on a click; never automatic, SP4a's rule for the RD suggestion, SP4a §8.1); `WorkerFailed` lowers N (the caps follow `liveWorkers()`, §3.8), and zero live workers, `StoreCorrupt` or a worker's `STORE_CORRUPT` (§2.6) show the failure panel with a reload link.
- **The first entry** keeps SP4a's rule: any error stops the load and shows the failure panel (§7.1).

### 3.7 Proto retention and `T(protoOnly)` (D11)

- **The rule** (master §4.2): K's proto is needed while K is in the proto ring (RD + 2 … RD + 3), or while a column of K's 3 × 3 is in the D set below Decorated; otherwise it may be freed (`store.freeProto`, at `protoReaders` 0), but only when K's status is ≥ Decorated. A column still at Proto keeps its proto (it is the column's only data, and its own D needs it; `reopenProto` could not restore it, §2.4).
- **Regeneration:** a D job whose 3 × 3 holds a column at status ≥ 2 without a live proto first gets `T(protoOnly)` for it: the `terrain` message with `protoOnly: true`, run by `reopenProto` (§2.4), scheduled as a T job at the D job's score.
- **The page's setting:** `retainAllProtos: true` (D11): nothing calls `freeProto`, and `T(protoOnly)` never runs on the page. The unit tests and the integration test (§8.5) run with retention on and check that every D still sees live protos and that the regenerated proto's region hash equals the original's. SP8b, whose features make the final set differ from the proto, turns it off (§12.6).

### 3.8 The adaptive throttle (`engine/throttle.ts`, D29)

`createThrottle({ max: max(1, N − 1) })` keeps `genCap` ∈ [1, max(1, N − 1)], starting at the maximum; `setMax(n)` re-clamps it, and the coordinator calls it whenever `liveWorkers()` changes (at N = 2 → 1 after a `WorkerFailed`, generation goes on with one job): fed every rAF tick's raw delta snapped to the display interval (the page's frame step feeds it before the FPS limiter, so a cap never reads as slow frames and never starves generation; amended while planning), whether generation (T, D, L) is in flight and the display interval (`push(frameMs, generating, intervalMs)`; a non-finite interval reads as 0); when the p95 of the last 60 frames exceeds max(16.7 ms, the display interval + 0.5 ms) while generation is in flight, `genCap` drops by 1 and the window restarts; after 120 consecutive frames under max(13 ms, the display interval + 0.5 ms) it rises by 1 (master §4.3). The thresholds follow the display (the user's decision of 2026-10-24, amended while planning): a display below 60 Hz does not read as permanently slow, a 60 Hz display can raise the cap again after a drop, and at 144-240 Hz they are 16.7 and 13 ms. The coordinator's caps: T + D + L in flight ≤ `genCap`, T ≤ max(1, N − 1), MESH ≤ N, total ≤ N, N = `liveWorkers()`. A ring buffer of 120 values and a 60-value scratch for the percentile, preallocated; the HUD and the bench JSON show `genCap`.

### 3.9 The upload budget and the per-column reveal (D13)

- **`createUploadBudget(ms, rows, now)`** (stays in `engine/uploadBudget.ts`): `start()` per frame, `exhausted()` when `ms` have passed or `rows` section rows were spent, `spend(rows)`, and `structural()`, which grants one structural operation per frame (a region's batch or arena created, grown in vertices, indices or instances, optimised or compacted) and only while no row was spent in this frame yet. While flying: 2 ms and 32 rows (`MEDIUM.uploadBudgetMs`, `uploadSections`, now read); while the loading screen is up: 12 ms, no row cap and no structural cap (every `structural()` call is granted while the 12 ms last, so the RD12 fill's ≈ 40 region creations and their growths do not each take a frame; a contract test covers both modes).
- **The layer boundary:** `render` may not import `engine` (`test/arch/rules/imports.ts:29`; SP4a passed `buildNext` a closure for the same reason). `render/sectionRenderer.ts` declares `interface UploadGate { exhausted(): boolean; spend(rows: number): void; structural(): boolean }`; engine's `UploadBudget` satisfies it structurally (no import either way), and the page (ui) passes the budget to `pump`.
- **The ready queue** is the section renderer's (§4.1): staged columns, each upload taking the nearest by `core/streamScore.ts`'s MESH score from the camera's column and yaw at the last rebuild (a linear scan over at most a few hundred staged columns, no allocation); a column's rows may span frames.
- **When the GPU sees the rows:** three uploads an object's pending update ranges only when the object passes frustum culling (`objects.update`, r186 `WebGLRenderer.js:1913-1915`), and merges whatever accumulated into one upload (`WebGLAttributes.js:103-147`). So the row cap alone does not bound a frame's upload: rows written beside or behind the camera (FOV 70°, the disc fills all around) would reach the GPU together on the first frame the user turns toward them, megabytes in one `render()`. The renderer owns the timing: a region object (RegionBatch's `BatchedMesh`, RegionMesh's arena `Mesh`) with rows written in this frame has `frustumCulled = false` for that frame, so its ranges upload under this frame's cap, and culling is restored once its attributes hold no pending range (`updateRanges.length === 0`). On RegionBatch, per-instance culling still draws nothing out of view; on RegionMesh one off-screen draw costs little. The same holds for RegionMesh's reveal-frame index writes and for removals.
- **The reveal:** a column is shown in the frame its last row is uploaded, all its rows in one call (master §4.2); nothing of a column is visible before. The LOD fill mask (SP11) will flip in the same call (`onColumnRevealed(cx, cz)`, a hook with no listener in SP4b).

### 3.10 Zero allocation at rest (D25)

Without movement or arriving results, the frame allocates nothing: the coordinator (preallocated table, heaps, scratch versions, the counts written into a caller-owned object), `pump` with nothing staged, the materials (`setFrameUniforms` writes into preallocated vectors; `fogRange`, `skyColors`, `sunDirection` gain `into` variants, `materials/index.ts:42-49`, `:112-130`), the lightmap (rebuilt only when its quantised inputs change, a day-factor or dusk step of 1/512 or a brightness change, into preallocated arrays: `lightmap.ts:35-36` today allocates and uploads every frame while time runs), frame timing (`frameTiming.ts:34`'s sorted copy into a preallocated scratch), the page's `FrameState` (one reused object, `worldPage.ts:588-595`) and the eye-light and height reads (§2.4). The HUD's refresh (a timer, `hud.ts:110`) is outside the frame and keeps its object.

### 3.11 The first entry (D21)

The page starts the coordinator at the spawn (or `?at`) with `holdReveals` on (§4.1): it calls `update(spawnCamera)` and `pump` (12 ms budget) every loading frame; the loading bar reads the coordinator's counts (SP4a's `progressFraction` over the needed MESH set). When every column of the MESH set is meshed and uploaded, the page compiles (the program of every pass a section can carry, opaque, cutout and translucent, built at load or not: a pass with no built section is compiled on a hidden one-triangle stand-in of the section renderer's own object kind, `BatchedMesh` or the region mesh, inside the same `compileAsync` walk, then freed, so the first water or glass met in flight links no program; the scene holds only the regions and the sky, so no other program is first used in flight; rulings R11), places the camera (SP4a D32), renders three warm-up frames with frustum culling off (§4.5), calls `revealAll()` and fades the overlay out (SP4a §8.4); then `holdReveals` turns off and the same coordinator streams.

### 3.12 Where SP4c attaches

SP4b builds one small API for SP4c's Apply, `bumpScope` (§2.7). SP4c builds the rest with Apply: the slot table's per-column `epoch`, MESH's "the 3 × 3 share the epoch" rule (master §5.1), and the renderers' swap of a revealed column (§4.4). The attachment points are the slot table's typed arrays (§3.1, one more column), the eligibility checks (§3.3) and the staging's per-column record (§4.1) (§12.1).

### 3.13 The interface

```ts
interface StreamCamera { readonly x: number; readonly z: number; readonly yawDeg: number }  // blocks, degrees
interface CoordinatorJobs {
  run(stage: Stage, cx: number, cz: number, protoOnly: boolean): Promise<JobOutcome>;
  cancel(pred: (stage: Stage, cx: number, cz: number) => boolean): void;

}
interface StreamStore {             // the page's attached store, as the coordinator needs it
  versionsInto(cx: number, cz: number, out: Int32Array): void;
  holder(cx: number, cz: number): 'free' | 'self' | 'other';
  freeColumn(cx: number, cz: number): void;
  freeProto(cx: number, cz: number): void;
}
interface StreamSink { stage(p: ColumnMeshPayload, seq: number): void; remove(cx: number, cz: number): void }
interface CoordinatorOptions {
  readonly jobs: CoordinatorJobs; readonly store: StreamStore; readonly sink: StreamSink;
  readonly throttle: Throttle; readonly rd: number; readonly rdMax: number; readonly retainAllProtos: boolean;
  readonly onEvent: (e: StreamEvent) => void;   // a skipped column, StoreFull, a fatal error
}
interface Coordinator {
  update(cam: StreamCamera): void;          // per frame; re-centres, unloads, issues; allocates nothing at rest

  firstFill(): boolean;                     // every MESH column of the current set meshed and handed to the sink

```
`createCoordinator(o)` validates `rd` before anything else, never runs work inside a Promise executor, and has no `load()` (the SP4a hand-overs, §7.6). The mesh job's levers (D27) live in `mesh/column.ts` and `mesh/fluid.ts`: the nine views fetched once per column and passed down, and `meshFluid` skipping the sections `fluidDepths` found dry; `mesh.section` must stay within its gates (§10).

### 4.2 RegionBatch (`render/regionBatch.ts`, D14)

- **Objects:** per region and pass a `BatchedMesh(1536, vertices, indices)` created at the region's first row of that pass (a structural operation), with `position` = the region's origin `(rx·128, −64, rz·128)` minus the floating origin and `perObjectFrustumCulled` on. Each row's instance matrix is `T(section offset inside the region)·S(1/8)`, set once (exact in float32: offsets ≤ (112, 368, 112)). `setOrigin` moves each region's `position` (about 20 objects at RD12), so the rebase costs no instance work, and instance ids may be reused freely (`addInstance` reuses them, `BatchedMesh.js:561-590`): SP4a's dense `origins` array (`regionBatch.ts:99`, `:133-144`) goes. The batch's own bounding sphere and box are set once to the region's box (radius ≈ 212 blocks), so three never recomputes them (ruling P16's caching, `:139-142`).
- **Reservations** (from SP4a's R4: median 430, p95 1,109 quads per column, so a full region holds ≈ 110k vertices at the median): opaque 131,072 vertices and 196,608 indices (≈ 1.8 MB of GPU buffers), translucent 16,384 / 24,576, cutout 8,192 / 12,288 created on demand (SP8a fills it).
- **Rows:** `addGeometry` (its sphere and box set before, SP4a's rule) and `addInstance` hidden (`setVisibleAt(false)`) as the budget allows; the reveal sets every row of the column visible in one call.
- **Removal:** `remove` hides the column's rows at once (`setVisibleAt(false)`, cheap) and marks them; `pump` releases them (`deleteGeometry` per row, which deletes its instance) under the frame's budget, each row counted against the row cap. `deleteGeometry` scans every `_instanceInfo` entry (`BatchedMesh.js:826-857`), up to 1,536 per batch, so 64 columns × 10-20 rows in one `update()` would be 1-2 M checks, far above the coordinator's ≤ 1 ms (the RD 12 → 8 drop of the bench's L6 does exactly this); under the row cap a frame spends at most 32 × 1,536 ≈ 50 k checks.
- **The instance cap:** a mountain region can hold up to 64 × 24 rows in the opaque pass, the 1,536 the batch was created with. When `addInstance` would exceed the cap (it throws "Maximum item count reached", `:561-570`), the row waits for a structural operation, `setInstanceCount(× 1.5)` (`:1266`); a contract case covers it.
- **Full reservations:** `addGeometry` only appends (`:627-712`), and deleted space comes back only through `optimize()`. When a row does not fit: `optimize()` if the region's deleted space is ≥ 40 % of its reservation, else `setGeometrySize` × 1.5; either is the frame's one structural operation, and the row waits for it. The spike measured them on the Iris Xe at 3.21 ms (`optimize`, on a 7.47 MB batch, larger than the ≈ 1.8-2.4 MB reservation) and 3.47 ms (× 1.5), and 32 re-adds at 0.47 ms (SP4a Spike evidence). **Those timings bound only the CPU half:** `spikeBench.ts:478-489` times the JS call alone, and the GL work happens in the next `render()` (`optimize`'s `bufferSubData` of every moved range, `BatchedMesh.js:917-950`; `setGeometrySize`'s new GL buffer and full upload, since the old geometry is disposed, `:1327-1380`). The GPU half is unmeasured, and on the Iris Xe it is the one in doubt, so the bench records every frame holding a structural operation (§8.3) and G1 checks that those frames also respect "no frame > 33 ms" (§8.4). In a straight flight a region fills at the front and empties behind, so neither is common; back-and-forth flying is where the 40 % rule acts.
- `setGeometryAt` is not used in SP4b (nothing remeshes a revealed column, §4.4).

### 4.3 RegionMesh (`render/regionMesh.ts`, D15)

- **The arena:** per region and pass one `Mesh` over one `BufferGeometry` with `position` Uint16 × 4 (region-local, SP4a §6.2's encoding), `data` Uint32 and a Uint32 index, of the same reservations as RegionBatch (opaque ≈ 2.4 MB: 12 B per vertex), created at the region's first row of that pass (structural). `setDrawRange(0, the index high-water mark)`.
- **Column ranges:** each column's rows of a pass occupy one contiguous vertex range and one index range, taken first-fit from a free list sorted by start and coalesced on release. Uploading a column writes its vertices (positions rewritten region-local, `data` copied) into its range and marks both attributes; its index range holds zeros (degenerate triangles: nothing is rasterised) until the reveal frame, when the rebased indices are written and that range is marked. Removal: `remove` zeroes the column's shown index range at once and marks it (the hiding, no merge); `pump` frees both ranges under the budget, as on RegionBatch, with the last row it releases (rulings R6). **Every range write is `addUpdateRange(start, count)` plus `needsUpdate = true`**: three uploads an attribute only when its `version` grew (`WebGLAttributes.js:211`), so a range alone uploads nothing.
- **Full arenas:** when no range fits, the arena is compacted if its free space is ≥ 40 % and would hold the span, else grown × 1.5; either is the frame's one structural operation (rulings R6).
  - **Compaction** is in place: the live columns' ranges are moved down with `copyWithin` in the same arrays (the index values rebased), then the whole attribute is uploaded (`clearUpdateRanges()`, then `needsUpdate = true`); no reallocation. While that whole upload is pending, a write adds no update range (r186 would send only the ranges, a partial upload), until three's upload callback clears the flag (rulings R6).
  - **Growth** cannot resize an attribute (three r186 throws "Resizing buffer attributes is not supported" when an array's byte length differs from its GL buffer's, `WebGLAttributes.js:211-215`), and swapping new attributes into the same geometry would leave the old GL buffers allocated until `geometry.dispose()`. So growth builds a new `BufferGeometry` with new attributes at 1.5 × the size, copies the live columns in, sets `mesh.geometry = next` and calls `prev.dispose()` in the same frame; `gpuBytes()` counts the new arena only (a contract test: after a growth, `gpuBytes()` equals the new arena's size, with no geometry left undisposed).
  - SP4a measured the whole RD12 load's merge at 31.2 ms on the Iris Xe and 18.2 ms on the RTX in Firefox (`flight-*-firefox.json`, `load.mergeMs`), about 2 ms per region; that is the CPU merge (`regionMesh.ts:127-163`), not the upload, so it bounds only the CPU half of one structural operation. The GPU half is measured as on RegionBatch (§4.2, §8.3).
- **Culling and order:** the region's sphere is the union of its shown spans' spheres, recomputed on each add or removal (≤ 64 spheres; rulings R6); translucent regions keep their back-to-front `renderOrder` (`regionMesh.ts:194-205`).
- three r186 applies every update range of an attribute with `bufferSubData` and clears them after the upload (`WebGLAttributes`), so a frame uploads only what changed, provided the object is drawn in that frame (§3.9).

### 4.4 The swap: SP4c's (D16)

No SP4b path stages a revealed column again: MESH is issued only for a Published, unmeshed column (§3.3), and a dropped MESH result is never staged (§3.6); its re-request stages a column that is not yet revealed, which replaces the staged one (§4.1). So in SP4b `stage(p, seq)` for a revealed column throws, and a coordinator unit test asserts that no revealed column is re-staged. SP4c builds the swap with Apply (master §4.2's "re-generation swaps atomically too"): the new rows uploaded hidden beside the visible old ones (RegionBatch: hidden instances; RegionMesh: new ranges with zero indices), then, in the frame the last new row is uploaded, the old rows removed and the new shown in one call. It attaches to the staging's per-column record (§4.1), which then also holds the old rows. The probe's `mixed` count (columns showing rows of two seqs) is already measured, and is 0 in SP4b.

### 4.5 Renderer fixes (`render/renderer.ts`)

- `warmUp` renders with `frustumCulled` off on every region, so the first entry uploads every region before the reveal (three uploads only what passes culling, r186 `WebGLRenderer.js:1913-1915`; the SP4a hand-over). While streaming, the same rule applies per frame to the regions with rows written in that frame (§3.9).
- The GPU timer deletes every pending query on a `disjoint` event (`renderer.ts:140-152`); `createGpuTimer` is exported and unit-tested with a fake extension; `withSectionsShown` is tested (hidden again after `compile`, `warmUp` and a throw).
- `setRenderDistance(rd)` sets `camera.far = cameraFar(rd)` and updates the projection (§5).

## 5. Live render distance (D18)
